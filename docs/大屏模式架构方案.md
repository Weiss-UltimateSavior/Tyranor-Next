# 大屏模式架构方案

> 生成日期：2026-09-12
> 目标设备：平板 / 大屏（含分屏、桌面窗口）
> 配套文档：架构约定见 `AGENT.md`，领域术语见 `CONTEXT.md`

## 1. 目标与范围

目标：为平板提供**独立的大屏 UI**（两套 UI 并行），两套 UI **共享同一功能层**；由应用设置开关控制，重启应用后生效。

范围：

- `app` 模块的 UI 层与表现层；新增共享表现层 `ui/state`。
- `core` 功能层保持两套 UI 共用；仅按需把锁在 composable 里的交互逻辑上移进表现层。
- 二级页面沿用现有 Activity 宿主，按模式切换内容，不新增 Activity。

非目标（本期不做）：

- 运行中热切换 UI（明确要求重启生效）。
- Navigation3 重构、引擎模块与原生引擎宿主 UI 适配。
- 新字号 / 新圆角 / 新配色规范（大屏若要偏离，需先登记 `AGENT.md`）。
- 折叠屏铰链姿态适配（列为后续）。

## 2. 关键决策

| 决策项 | 结论 |
| --- | --- |
| UI 形态 | 单独一套大屏 UI（`ui/wide`），不做同一套响应式压缩 |
| 功能层 | 两套共享 `core` + 新增共享表现层 `ui/state` |
| 模式选择 | 三态设置：跟随设备 / 强制大屏 / 强制小屏，默认跟随设备 |
| 生效时机 | 进程启动时快照一次，重启应用生效；运行中旋转/分屏不切换模式 |
| 二级页 | 不新增 Activity，`AppScreenActivity` 宿主内按模式换内容 |
| 导航与视觉 | 大屏导航形态、页面样式后续逐步实现，本方案只定结构与入口 |

## 3. 总体架构

```text
ui/compact（现有 ui/home | ui/game | ui/engine | ui/settings | ...）
        │
        ├──────────────┐
ui/wide（新）           │
        │              ▼
        ├──→ ui/common/*   共享视觉资产（AppTopBar / AppNavItem / AppAlertDialog /
        │                  AppScreenScaffold / AppUiMode / AppWindowWidth / AppRelaunch）
        │
        └──→ ui/state/*    共享表现层（ViewModel / StateHolder / Reducer / Actions）
                    │
                    ▼
              core/*       功能层（游戏库/启动/封面/存档/补丁/设置/授权/更新）
                    │
                    ▼
              engine/*     底层引擎层
```

职责边界：

| 层 | 归属 | 两套 UI 是否共享 |
| --- | --- | --- |
| 功能层 | `core/*` | 是（业务读写、持久化、扫描、启动编排等） |
| 共享表现层 | `ui/state/*` | 是（页面状态、动作、状态归约） |
| 共享视觉资产 | `ui/common/*` | 是（AGENT 强制统一的组件） |
| 手机 UI | 现有 `ui/<feature>/*` | 否 |
| 大屏 UI | `ui/wide/*` | 否 |

## 4. 模式模型与生效机制

### 4.1 两个概念分离

| 概念 | 性质 | 作用 |
| --- | --- | --- |
| `AppUiMode { COMPACT, WIDE }` | 进程级稳定，设置决定，重启生效 | 选哪一套 UI 树 |
| `AppWindowWidth { Compact, Medium, Expanded }` | 运行时随窗口变化 | 只在大屏套件内部做二级排版（单双栏、列数） |

### 4.2 进程级快照（核心约束）

`AppUiMode` 不能每次从 prefs 现读：否则用户改了设置但未重启时，旋转/分屏导致的 Activity 重建会提前切换 UI，与「重启生效」语义不符。

- `AppUiModeHolder.current` 在进程内解析一次；
- 进程内任何 Activity 重建（旋转、分屏、深色切换）都读取同一快照；
- 只有真正的冷启动（Application 重建）才会重新解析。

### 4.3 auto 判定

- `auto` 使用 `resources.configuration.smallestWidthDp >= 600` 判定设备类型，而不是当前窗口宽度；
- 原因：平板上分屏后窗口宽度可能低于 600dp，但设备仍应使用大屏套件，避免分屏时 UI 树跳变；
- `AppWindowWidth` 负责在同一套 UI 内响应窗口变化。

## 5. 目录结构与共享边界

```text
app/src/main/java/com/tyranor/next/ui/
├── common/                  # 共享视觉资产（两套 UI 均可 import）
│   ├── AppUiMode.kt         # AppUiMode / LocalAppUiMode / AppUiModeContent / Holder / Resolver
│   ├── AppWindowWidth.kt    # 运行时窗口宽度档
│   ├── AppRelaunch.kt       # 重启应用工具
│   └── （现有 AppTopBar / AppNavItem / AppAlertDialog / AppScreenScaffold / ...）
├── state/                   # ★ 共享表现层（新）
│   ├── library/             # MainLibraryViewModel 及 Reducer（自 ui/main 迁入）
│   ├── game/                # 游戏页交互状态（阶段 B 抽取）
│   └── save|patch|...       # 按需逐步抽取（阶段 C）
├── main/ home/ game/ engine/ settings/ cover/ patch/ save/ auth/
│                            # 手机（Compact）UI，现有包结构不动
└── wide/                    # ★ 大屏 UI（新）
    ├── WideMainNavigation.kt
    ├── home/WideHomeScreen.kt
    ├── game/WideGameScreen.kt
    ├── engine/WideEngineScreen.kt
    ├── settings/WideSettingsScreen.kt
    └── save|patch|pergame/...   # 二级页大屏变体（阶段 C）
```

依赖规则（写入 `AGENT.md`）：

```text
ui/wide | 现有 ui/<feature>  → ui/common, ui/state, core
ui/wide                      ↛ 现有 ui/<feature> 的内容文件（UI 壳/活动宿主除外）
ui/state                     ↛ ui/wide, 现有 ui/<feature>
ui/common                    ↛ ui/wide, ui/state（只允许被依赖）
```

- 「UI 壳/活动宿主」指 `MainNavigation`、各 `*Activity` 这类分支入口文件；会话内仅允许它们同时 import 两套 UI，且只做 `AppUiModeContent` 分发。
- 手机包名不强制改为 `ui/compact`，避免大面积重命名；文档中称其为 **Compact UI**，`ui/wide` 为 **Wide UI**。

## 6. 共享表现层（ui/state）

### 6.1 现状差距

游戏库层面已经符合共享表现层形态：`MainLibraryViewModel` + `MainLibraryStateReducer` 承载库 / 最近 / 快捷 / 搜索状态，但存在两个问题：

1. 位置在 `ui/main/`（手机目录），wide 引用会形成 wide → compact 反向依赖；
2. 游戏页交互逻辑仍内嵌在 composable 中：`GameScreen.kt` 内有 13 处 core 服务直调（启动、快捷方式、封面搜索/绑定/自定义、启动文件等），大屏 UI 若不复用就必须复制。

### 6.2 抽取原则

- 表现层承载**状态 + 动作 + 归约**，承载任何与 IO / 业务相关的流程；
- **呈现决策留在 UI**：状态给出数据（如 `candidates/loading/error`），compact 用弹窗、wide 用侧栏，各自实现；
- `ui/state` 内禁止 import 布局 / 弹窗 / 主题组件，保持两套 UI 可消费；
- 只被某一套 UI 使用的**纯视觉状态**（如「哪一栏展开」）不必上移，可留在对应 UI 内并用 `rememberSaveable`。

### 6.3 首批抽取清单

| 来源 | 建议落点 | 内容 |
| --- | --- | --- |
| `ui/main/MainLibraryViewModel.kt` | `ui/state/library/` | 整文件迁移（含 `MainLibraryStateReducer`、`mergeChangedGameFields`）；同步更新 `app/src/test/.../ui/main/MainLibraryStateReducerTest.kt` 的 package 与 import |
| `ui/game/GameScreen.kt` | `ui/state/game/` | 启动（含 Artemis 补丁询问）、快捷方式与裁切、封面搜索 / 绑定 / 自定义、启动文件列表、刮削触发 |
| `ui/save/SaveManagementActivity.kt` | `ui/state/save/` | 任务互斥 / 导出导入 / 刷新（阶段 C） |
| `ui/patch/KrkrOnlinePatchActivity.kt` | `ui/state/patch/` | 索引加载 / 安装任务 / 取消态（阶段 C） |

## 7. 入口与宿主改造

1. `MainActivity.setContent` 注入模式：
   ```kotlin
   CompositionLocalProvider(LocalAppUiMode provides AppUiModeHolder.current) {
       MainNavigation()
   }
   ```
2. `MainNavigation()` 变为纯分发器：`WIDE → WideMainNavigation()`，否则走现有手机壳；四页常驻组合动画逻辑建议抽成共享 `MainTabHost`（性能关键逻辑不复制；如不抽则 wide 版本需注明同步维护）。
3. `AppScreenActivity.setAppScreenContent` 同样注入 `LocalAppUiMode`；二级页内容用统一分支组件：
   ```kotlin
   AppUiModeContent(
       compact = { SaveManagementScreen(game) },
       wide = { WideSaveManagementScreen(game) },
   )
   ```
4. 启动参数（`ScanGameIntents`、`LaunchContract`）与引擎宿主完全不动。

## 8. 设置与重启

- `AppSettingsStore`（core，无 Compose）新增：
  - `KEY_LARGE_SCREEN_MODE`，取值常量 `LARGE_SCREEN_MODE_AUTO|WIDE|COMPACT`，默认 `auto`；
  - `getLargeScreenMode(context)` / `setLargeScreenMode(context, value)`。
- `AppSettingsActivity` 新增「大屏模式」下拉（跟随设备 / 强制大屏 / 强制小屏）；保存后弹 `AppAlertDialog`：提示需要重启生效，提供「立即重启 / 稍后」。
- `AppRelaunch.relaunch(context)`：`packageManager.getLaunchIntentForPackage` + `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK` 启动后 `Process.killProcess(Process.myPid())`。
- 重启前：Holder 仍是旧值，旋转/重建不会切换；冷启动后：Holder 解析新值生效。

## 9. 大屏套件内的窗口响应

- `ui/wide` 内部统一使用 `AppWindowWidth`（`<600 / 600–839 / ≥840`）决定单双栏、列数、面板形态；
- 禁止再散写字面量判断；现有 `isWideScreen()` 只保留在 Compact UI 内部（游戏页列数、首页快捷启动），不再扩散；
- 阶段 A 骨架期：`WideMainNavigation` 可先临时复用现有四个页面内容 + 简单导航壳，保证「强制大屏」可跑通，随后逐页替换为 `ui/wide` 实现。

## 11. 实施阶段

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| A 骨架 | `AppUiMode` 系列、`AppRelaunch`、设置项 + 重启弹窗、`ui/wide` 占位；`MainLibraryViewModel` 迁入 `ui/state/library` | 手机 `auto` 保持现状；平板 `auto` 进大屏壳；手机强制档可切换两套（重启生效）；手机 UI 无行为回归 |
| B 游戏页 | 抽取 `GameScreen` 交互到 `ui/state/game`（纯重构），再实现 `wide/game` | compact 行为不变；wide 直接复用同一状态入口 |
| C 其余页 | save / patch / coverscraper / engine / settings 按需抽取 + wide 变体 | 全页面无拉伸；两套行为一致 |
| D 精细化 | 窗口 resize / 分屏 / 折叠屏；大屏二级排版 | 分屏、旋转不崩溃，状态可恢复 |

## 12. 防漂移规则

新增任何交互前先自检：**wide 能否直接调用 `ui/state` 的同一入口？** 不能则先把逻辑上移，再写两套呈现。

可选自动化（后续加类似 `checkHardcodedUiStrings` 的检查任务）：扫描 import，禁止 `ui/wide` 引入现有 `ui/<feature>` 内容包、禁止 `ui/state` 引入 UI 包。

## 13. 回归与验收

| 场景 | 预期 |
| --- | --- |
| 手机 `auto` / 强制小屏 | 与当前版本一致，无布局与行为回归 |
| 平板 `auto` | 进入大屏 UI；旋转、分屏不切换模式 |
| 手机强制大屏 | 大屏 UI 可运行（供逐步调样式） |
| 设置切换后 | 未重启不生效（旋转同样不生效）；「立即重启」后生效 |
| 二级页 | 宿主内正确分支；返回栈与传参不受影响 |
| 引擎启动 | 不因 UI 模式变化受影响（extras / 宿主不变） |
| 旋转 / 分屏 / 深浅色 / 三语言 | 两套 UI 均正常，关键状态可恢复 |

## 14. 风险

- **双 UI 维护成本**：靠「共享边界白名单」控制；共用组件优先放 `ui/common`，业务逻辑必须放 `ui/state`。
- **状态恢复**：模式不热切换，但旋转/分屏仍会重建 Activity；两套 UI 均需用 `rememberSaveable` / ViewModel 保存选中项、弹窗、滚动位置。
- **规范约束**：两套 UI 必须继续遵守 AGENT 的 AppTopBar、两档字号、8dp 圆角、颜色常量；大屏如需偏离，先登记规范豁免。
- **测试成本**：需同时覆盖手机、平板（现成 `Pixel_Tablet` AVD）、平板分屏三种窗口形态。

```kotlin
// ui/common/AppUiMode.kt
enum class AppUiMode { COMPACT, WIDE }

val LocalAppUiMode = staticCompositionLocalOf { AppUiMode.COMPACT }

@Composable
fun AppUiModeContent(compact: @Composable () -> Unit, wide: @Composable () -> Unit) {
    if (LocalAppUiMode.current == AppUiMode.WIDE) wide() else compact()
}

object AppUiModeHolder {
    @Volatile
    private var resolved: AppUiMode? = null

    /** TyranorNextApplication.onCreate 调用一次；进程内只解析一次。 */
    fun init(context: Context) {
        if (resolved == null) {
            resolved = AppUiModeResolver.resolve(context.applicationContext)
        }
    }

    /** 正常启动流程已由 Application 初始化；未初始化时按 Compact 兜底。 */
    val current: AppUiMode
        get() = resolved ?: AppUiMode.COMPACT
}

object AppUiModeResolver {
    fun resolve(context: Context): AppUiMode = when (AppSettingsStore.getLargeScreenMode(context)) {
        AppSettingsStore.LARGE_SCREEN_MODE_WIDE -> AppUiMode.WIDE
        AppSettingsStore.LARGE_SCREEN_MODE_COMPACT -> AppUiMode.COMPACT
        else -> if (context.resources.configuration.smallestScreenWidthDp >= 600) {
            AppUiMode.WIDE
        } else {
            AppUiMode.COMPACT
        }
    }
}
```

```kotlin
// ui/common/AppWindowWidth.kt
enum class AppWindowWidth { Compact, Medium, Expanded }

internal fun appWindowWidth(widthDp: Int, smallestWidthDp: Int): AppWindowWidth {
    val effective = if (smallestWidthDp >= 600) maxOf(widthDp, 600) else widthDp
    return when {
        effective < 600 -> AppWindowWidth.Compact
        effective < 840 -> AppWindowWidth.Medium
        else -> AppWindowWidth.Expanded
    }
}

@Composable
fun rememberAppWindowWidth(): AppWindowWidth =
    LocalConfiguration.current.let { c ->
        remember(c.screenWidthDp, c.smallestScreenWidthDp) {
            appWindowWidth(c.screenWidthDp, c.smallestScreenWidthDp)
        }
    }
```

```kotlin
// ui/common/AppRelaunch.kt
object AppRelaunch {
    fun relaunch(context: Context) {
        val intent = context.packageManager.getLaunchIntentForPackage(context.packageName) ?: return
        intent.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK)
        context.startActivity(intent)
        Process.killProcess(Process.myPid())
    }
}
```
