# 三层架构目录归类优化方案

## 实施状态

本方案已落地到当前工作区：

- 功能抽象层已迁移到 `app/src/main/java/com/tyranor/next/core/`。
- UI 层已按页面域迁移到 `app/src/main/java/com/tyranor/next/ui/`。
- 旧 `scanner`、`settings`、`updater`、`ui/pages` 主源码包已清空并移除。
- 共享 Native 插件 so 以 `engine/src/main/nativeplugins` 为源头，App 侧保留 manifest 与 app-only 插件，由 Gradle 构建期合并打包。
- 共享 RPGMaker 脚本 `__rmmz__.js`、`__hook_rmmz_core.js`、`__hook_rmmz_managers.js` 以 `engine/src/main/assets` 为源头，由 Gradle 构建期生成到 app assets。
- `AGENT.md` 已补充三层架构目录规范，后续新增文件按本方案归类。

## 目标

将当前项目按职责明确归类为三层：

1. 底层引擎层：负责真实引擎运行、Native/JNI、引擎宿主 Activity、引擎资源与插件加载。
2. 功能抽象层：负责把 App 侧业务意图转换成可执行能力，包括游戏扫描、启动、封面、存档、补丁、设置、更新等。
3. 界面 UI 交互层：负责 Compose 页面、Activity 壳、导航、弹窗、主题、用户交互与状态展示。

目标不是一次性大搬家，而是在不破坏现有功能的前提下，逐步让依赖方向稳定为：

```text
界面 UI 交互层
    ↓
功能抽象层
    ↓
底层引擎层
```

底层引擎层不得反向依赖 App UI；UI 层不得直接依赖引擎实现类；跨层通信统一经过功能抽象层。

## 当前结构概览

当前项目是标准 Android 多模块工程：

```text
TyranorNext/
├── app/       # 应用入口、Compose UI、功能抽象层、应用资源
├── engine/    # 引擎宿主、Native/JNI、SDL/Cocos/IJK、引擎资源
├── docs/      # 方案文档
├── gradle/    # Gradle Wrapper 与版本目录
├── .github/   # CI/CD
└── build.gradle.kts / settings.gradle.kts / gradle.properties
```

模块边界整体是合理的：

- `app` 是最终应用模块，依赖 `engine`。
- `engine` 是 Android Library，承载底层引擎能力。
- UI 当前没有直接 import `com.core`、`org.tvp`、`org.libsdl`、`bridge` 等底层引擎包。
- 主要改造点集中在 `app` 内部包职责：原 `scanner` 包已拆入 `core/*`，原 `ui/pages` 已拆入各 UI 功能域。

```text

├── src/main/nativeplugins/
└── src/main/AndroidManifest.xml
```

### 职责

- 各引擎宿主 Activity：
  - Kirikiri/Kirikiroid
  - krkrsdl3
  - ONScripter
  - Artemis
  - Tyrano
- Native/JNI 桥接：
  - `krkr_bridge.cpp`
  - `bridge.NativeBridge`
  - `bridge.KrSafMirror`
  - `bridge.KrPathUtils`
- SDL、SDL3、Cocos2dx、IJK 等第三方/移植层代码。
- 引擎侧资源、脚本、字体、CSB UI、Native so。
- Native 插件安装、查找、加载、版本兼容。
- 引擎进程内偏底层的偏好与 UI 文案，例如 `EnginePrefs`、`EngineThemeColors`、`EngineUiText`。

### 层级规则

- 可以依赖 Android Framework、DocumentFile、Native/JNI、引擎第三方库。
- 不应依赖 `com.tyranor.next.ui.*`。
- 不应依赖 App 页面状态、Compose 组件、ViewModel。
- 不应直接决定 App 游戏列表、封面列表、设置页的展示逻辑。
- 引擎启动所需参数通过 Intent、extras、文件路径、Uri、插件管理接口传入。

### 后续优化点

- 保持 `engine` 模块作为底层边界，不建议把 UI 页面迁入 `engine`。
- `bridge` 包名较泛，后续可考虑移动为 `com.core.bridge` 或按引擎拆分为 `com.core.kirikiri.bridge`。
- `engine/src/main/nativeplugins` 与 `app/src/main/nativeplugins` 存在重复资源，需要明确 source-of-truth。
- `engine/src/main/assets` 与 `app/src/main/assets/engine` 存在部分重复脚本，需要明确哪些是引擎运行资源，哪些是 App 打包/注入资源。

## 资源归属方案

### 当前问题

当前存在两类重复资源：

1. `app/src/main/assets/engine` 与 `engine/src/main/assets` 存在部分重复脚本。
2. `app/src/main/nativeplugins` 与 `engine/src/main/nativeplugins` 存在重复 Native 插件 so。

其中部分脚本完全相同，部分脚本同名但内容不同。这个状态需要明确资源源头，否则后续维护容易出现“一边更新、一边漏改”。

### 推荐规则

- `engine/src/main/assets`：引擎运行时直接依赖的原始资源。
- `app/src/main/assets/engine`：App 启动或注入流程需要随应用打包下发的业务资源。
- `engine/src/main/nativeplugins`：底层引擎可直接使用的插件/库资源。
- `app/src/main/nativeplugins`：App 首次启动安装到私有目录的插件包源。

如果同一份文件需要同时进入两处目录，应优先建立构建期复制/打包任务，避免手工维护双份文件。

### 后续目标

```text
source-of-truth/
    ↓ build task
generated/copied assets
```

最终应做到：

- 手工编辑只发生在一个源头目录。
- 打包产物由 Gradle 任务生成。
- 文档中写明每类资源由谁维护。
- CI 中检查重复资源是否意外漂移。

```text
功能抽象层 core 拆包
  ↓
UI 页面域拆包
  ↓
资源 source-of-truth
  ↓
构建脚本整理
  ↓
测试与实机回归
```

每一阶段都应保持可构建、可运行、可回滚。

## 风险点与控制策略

| 风险 | 影响 | 控制策略 |
| --- | --- | --- |
| 大量包名迁移导致 import 漏改 | 编译失败 | 每迁移一组就运行单元测试或 assembleDebug |
| Manifest Activity 路径漏改 | 二级页面打不开 | UI Activity 迁移后重点检查 Manifest |
| UI 层误引底层引擎类 | 层级再次穿透 | 增加 `rg` 检查规则 |
| 同名资源内容不同 | 运行时资源错用 | 先建立资源用途清单，再做单源化 |
| Native 插件路径变化 | 引擎启动失败 | 保持打包产物路径不变，仅调整源头 |
| 测试包路径未迁移 | 测试失效 | 与源码迁移同批调整 test import |
| AGENT.md 规则滞后 | 后续实现继续走旧结构 | 第一阶段先修文档 |

## 建议增加的结构检查

可以在后续 CI 或本地脚本中加入简单检查：

```bash
rg "import (com\\.core|com\\.akira|com\\.yuri|org\\.tvp|org\\.libsdl|org\\.cocos2dx|bridge\\.)" app/src/main/java/com/tyranor/next/ui
```

期望结果为空。若出现结果，说明 UI 层直接依赖了底层引擎层。

```bash
rg "package com\\.tyranor\\.next\\.scanner" app/src/main/java app/src/test
```

迁移完成后期望结果为空。

## 判断标准

后续新增文件时，按以下问题判断归属：

1. 是否直接运行/适配某个引擎、Native、SDL、Cocos、IJK？
   - 是：放入底层引擎层。
2. 是否处理扫描、启动、封面、存档、补丁、配置、更新、账号授权等业务能力？
   - 是：放入功能抽象层。
3. 是否负责页面、弹窗、主题、导航、按钮、列表、用户输入？
   - 是：放入界面 UI 交互层。

如果一个文件同时命中多个层级，优先拆分。UI 只保留交互，业务流程下沉到功能抽象层；功能抽象层只保留编排，真实引擎细节下沉到底层引擎层。
