## 1. 背景与目标

现状：

- 虚拟按键只有 RPG Maker MV/MZ 有，且是注入 WebView 的 1600 行 JS（`__touch_pad.js`），布局模型只有 `{x, y, scale, visible}`，按钮集合固定、不可增删、不可改键、不支持多键输出与长按/双击语义。
- 没有任何手柄映射能力：SDL 系宿主的 SDL 手柄管线对 Kirikiri/ONS 类引擎等于摆设，Kirikiri2 的按键白名单直接吞掉 `KEYCODE_BUTTON_*`。
- 配置持久化依赖引擎子进程回写 prefs blob（整条读改写），是已知的跨进程限制点。

目标：

1. **可编辑虚拟按键**：按钮可增删、拖拽、缩放、改样式、改输出键位；支持按住/长按/单击/双击多触发时机与多键输出（含鼠标键）；游戏内所见即所得编辑 + 应用内方案管理。
2. **手柄按键重映射**：手柄（按键/摇杆/扳机/D-Pad）映射到键盘键与鼠标键，支持全局映射与每游戏覆盖，支持按住保持（toggle）语义。
3. **覆盖所有内置引擎**（8 类宿主），Web 系（Tyrano/MV/MZ/VN/WebOther）一并纳入。

明确边界：**外置 APK 引擎（Ren'Py / RGSS RPGM / Winlator / 模拟器）不在覆盖范围**——输入注入必须发生在游戏进程内，主 App 无法向其他 App 注入按键（除非引入无障碍服务，代价与体验不可接受）。

### 为什么覆盖层不能整体搬到 app 层

引擎宿主均在独立进程（`:kirikiri2`、`:krkrsdl3`、`:siglus`、`:fvp`、`:tyrano`、`:rpgmaker` 等），app 进程无法向另一个进程的 Activity 窗口添加 View；按键注入（`nativeKeyAction`、`SDLActivity.onNativeKeyDown`、`fbKey`、`rfvp_android_key`、`EmulateKeyEvent`）也都是进程内调用。因此切分为：

- **engine 层**：输入内核（canonical 键位、路由器、各宿主 InputSink）+ 虚拟按键覆盖层与游戏内编辑模式；
- **app 层**：配置数据（方案/映射）、存储与迁移、设置页（方案管理与手柄映射 UI、导入导出）。

依赖方向沿用三层架构（ui → core → engine），不引入反向依赖。

## 2. FCL 参考实现分析（结论摘要）

### 2.1 可编辑虚拟按键

**数据模型**（`FCL/src/main/java/com/tungsten/fcl/control/data/`）：

| 类 | 内容 |
|---|---|
| `ControlButtonData` | id、text、style、baseInfo、event；可克隆（副本偏移 2% 防重叠） |
| `BaseInfoData` | 位置 0..1000（对屏宽/高比例），尺寸 PERCENTAGE/ABSOLUTE 双模式 + 参考边（SCREEN_WIDTH/SCREEN_HEIGHT），visibilityType |
| `ButtonEventData` | 开关：pointerFollow / movable / swipable；四个触发时机：press / longPress / click / doubleClick |
| `ButtonEventData.Event` | 每个时机可配：`outputKeycodes[]`（多键）、`outputText`、autoKeep（按下保持）、autoClick（连点）、openMenu / switchTouchMode / switchMouseMode / input（文本）/ quickInput（功能动作）、bindViewGroup[]（切换控件组） |
| `ControlViewGroup` | 控件分组与显隐（不同场景切换不同按钮集） |
| `ButtonStyles` / `DirectionStyles` | 具名共享样式（颜色/描边/圆角/按下态） |

**渲染与编辑**（`control/view/`）：`ViewManager`（29KB，编辑态核心）、`ControlButton`/`ControlDirection`/`TouchPad` 自绘 View、`ControlEditBar`（跟随选中控件的悬浮操作栏：设置/复制/删除）；编辑交互 = 拖拽移动 + 缩放手柄/滑杆改尺寸 + `EditButtonDetails`（属性页：文本/位置/尺寸/样式 + 事件 Tab）+ `SelectKeycodeDialog`（键位网格，`KeycodeView` 多选，含鼠标区）。

**输出**：所有控件与手柄最终都走一个出口——`FCLInput.sendKeyEvent(keycode, keyChar, press)`，鼠标码经 `MOUSE_MAP` 走 `pushEventMouseButton`，其余经 `pushEventKey` 送入游戏桥（`control/FCLInput.java:112`）。

**存储与分发**：布局为独立 JSON（`assets/controllers/00000000.json` 内置默认，约 30KB；`control/download/` 提供控制器索引下载；`mio/controlconverter/` 有 FCL↔Zalith 格式互转）。

### 2.2 手柄按键重映射

（`control/gamepad/`）

- **逻辑按钮集**固定 20 个：A/B/X/Y、START/SELECT、L1/R1、L2/R2、L3/R3（THUMBL/THUMBR）、DPAD 四向、左摇杆仿真方向 DIRECTION_FORWARD/BACKWARD/LEFT/RIGHT。
- `GamepadMap` 每项 = `keycodes[]`（多键输出）；默认键位以 Minecraft 习惯给（A→Space、B→Q、X→E、Y→F、左摇杆→WASD、肩键→滚轮、扳机→鼠标左右键、L3→Ctrl、START→Esc、SELECT→Tab）。
- `GamepadEmulatedButton`：按下/抬起状态机，仅在状态翻转时发送；`GamepadButton` 扩展 toggle 语义（按一下持续按住，再按释放，用于潜行类）。
- 输入采集：`Gamepad.handleKeyEventInput` / `handleMotionEventInput`（基于第三方 `fr.spse.gamepad_remapper` 库做按键归一）；摇杆轴 X/Y/Z/RZ、扳机 LTRIGGER/RTRIGGER（阈值 0.5）、HAT_X/Y（阈值 0.85）分别路由到逻辑按钮。
- 事件来源过滤：只有 `SOURCE_GAMEPAD` 的设备事件进入映射，外接键盘不受影响。
- 持久化：`files/gamepad.json`（Gson 直存 `GamepadMap`）。
- UI：`GamepadMapDialog` + `GamepadMapItemAdapter`（应用内对话框绑定）。

### 2.3 对我们最有价值的结论

1. **两功能共用一个输出层**：控件按钮与手柄按钮最终是同一件事——"输入源 → 键位序列 → 游戏"。FCL 里两者共用 `sendKeyEvent`；我们也应共用一个 canonical 键位空间 + 各宿主 InputSink，而不是做两套。
2. **数据驱动 + 多键输出 + 多触发时机**：这是"按钮可编辑"的完整含义，比现有 `{x,y,scale,visible}` 模型高一个量级，应直接采纳其模型而非修补旧 JS。
3. **编辑器在游戏内（WYSIWYG）**：FCL 用悬浮编辑栏 + 属性对话框 + 键位网格对话框完成全部编辑，不依赖 PC/设置页；这是成熟 UX，我们照此实现原生编辑态。
4. **具名样式 + 控件组 + 导入导出**：低成本获得用户间分享布局的能力。

### 2.4 必须改造的点

| 维度 | FCL | 我们 |
|---|---|---|
| 注入目标 | 单一运行时（LWJGL/GLFW 桥），键位空间唯一 | 8 类宿主注入 API 各不相同 → 需要 canonical 键位 + 每宿主转换器 |
| 键位空间 | GLFW keycode + 1000+ 鼠标伪码 | 以 Android KeyEvent keycode 为基（宿主天然接受），+ 1000 段鼠标码，+ 2000 段动作码 |
| 覆盖层 | 仅 Launcher 进程（Minecraft 内嵌） | 各引擎宿主进程内各挂一份，engine 模块共享同一 `VirtualPadView` |
| 存储 | 全局 `gamepad.json` + 控制器 JSON | 方案文件 + 每游戏选择键（复用现有单游戏覆盖体系）+ 迁移旧 touchpad 配置 |
| 编辑入口 | 游戏内菜单 | 游戏内原生 FAB（可拖动，参考 `VirtualMouseLayer` 手柄钮模式）+ 应用内方案管理页 |

## 3. 总体架构

### 3.1 数据流

```
输入源                                 canonical 空间               宿主适配                   引擎
┌─────────────────┐
│ 物理手柄 按键/轴 │──┐
├─────────────────┤  │   ┌──────────────────┐   ┌──────────────┐   ┌────────────────────┐
│ 虚拟按键覆盖层   │──┼──▶│ InputRouter      │──▶│ InputSink     │──▶│ nativeKeyAction    │ KRKR
│ (VirtualPadView)│  │   │ ·死区/滞回/方向合成│   │ (每宿主一份) │   │ SDLActivity.onNative... │ ONS/krkrSdl3
├─────────────────┤  │   │ ·多键/toggle/长按  │   │              │   │ forwardKey(VK)     │ Siglus
│ 物理键盘(顺带)   │──┘   │ ·消费策略/文本期放行│   │              │   │ NativeGames.fbKey  │ RL/AVG32/UK2
└─────────────────┘       └──────────────────┘   │              │   │ NativeRfvp.keyEvent│ FVP
                                                  │              │   │ EmulateKeyEvent    │ Artemis
                                                  │              │   │ JS keydown/keyup   │ Web 系
                                                  └──────────────┘   └────────────────────┘
```

### 3.2 canonical 键位空间

- **键盘段**：直接采用 `android.view.KeyEvent.KEYCODE_*` 整数值（宿主大多原生接受；Siglus/Framebuffer/FVP/Artemis/Web 由转换器映射到各自空间）。
- **鼠标段**（1000..1099）：`1000 MOUSE_LEFT`、`1001 MOUSE_RIGHT`、`1002 MOUSE_MIDDLE`、`1003 SCROLL_UP`、`1004 SCROLL_DOWN`（对齐 FCL 习惯，`__touch_pad.js` 现有按钮语义可平移）。
- **动作段**（2000+，v1 仅定义 2000）：`2000 ACTION_SCREENSHOT`（截屏：从当前游戏窗口取一帧保存为 PNG，宿主经 `InputSink.performAction` 处理）。草案中的 `2000 TOGGLE_PAD` 未实现——按键层显隐由 FAB 点按承担（`VirtualPadView`）。后续可扩展切换方案、呼出修改器等。
- 转换器：`Android → JS keyCode`（Web，新建小表：Enter 66→13、Esc 111→27、方向 19..22→38..40、Space 32→32、Ctrl 113/114→17、Shift 59/60→16、字母同值等）、`Android → Windows VK`（Siglus 已有 `vkCodeFor`，Artemis 已有表）、`Android → fbKey`（`FramebufferGameActivity.mapKey` 反向复用）、`Android → rfvp VK`（FVP）。

### 3.3 宿主适配清单（已验证注入点）

> 接入状态：表中「现有输入入口」列均为代码中**已核实**的注入点；**截至当前只有 Web 行已接入**
> （`InputRemapController.installWeb` 装配 Tyrano/RpgMaker 两个 Web 宿主），其余宿主按同一接口
> 后续接入（见 §7 阶段 1/3）。

| 宿主 | 现有输入入口 | 注入方式 | 备注 |
|---|---|---|---|
| Kirikiri2 | `KrGLSurfaceView.onKeyDown/Up`（白名单仅 BACK/ENTER/MENU/DPAD） | 路由直调 `KR2Activity.nativeKeyAction(keyCode, down)`（public static native，KR2Activity.java:319），绕过白名单 | 鼠标码可走 `nativeTouchesBegin/End`（317-323） |
| ONS | `ONScripter extends SDLActivity` | `SDLActivity.onNativeKeyDown/Up(keyCode)`（public static native，SDLActivity.java:548） | 已有 ESC 直调先例 |

### 3.4 事件管线与消费策略

- 拦截点：**现状**——两个 Web 宿主（`TyranoActivity` / `RpgMakerActivity`）已在 `dispatchKeyEvent` /
  `dispatchGenericMotionEvent` 最前接入 `InputRouter`（经 `InputRemapController.installWeb`）；
  **规划**——其余宿主（KRKR / Siglus / Framebuffer / FVP / Artemis）在 `Activity.dispatchKeyEvent` /
  `dispatchGenericMotionEvent`（早于 View 树与 WebView）最前接入，先过 `InputRouter`。
- 手柄识别：`event.source` 含 `SOURCE_GAMEPAD`/`SOURCE_JOYSTICK`，且非字母键盘设备（对齐 FCL `Gamepad.isGamepadEvent`）。
- **命中映射即消费**（`return true` 不调 super），避免 SDL 系宿主二次分发；BACK 键永不消费。
- **文本输入期放行（未实现，规划）**：`__tyranor_input.js` 目前**无条件**合成 keydown/keyup，
  无编辑框/`activeElement` 判断；KRKR `KrInputConnection`、Siglus IME 通道的「IME 激活时路由让行」
  是后续接入项（见 §8 风险），防止影响游戏内命名输入。
- 摇杆仿真方向：死区默认 0.35、滞回 0.05；八向可配；只在方向集合变化时发 down/up（同现有 JS 逻辑），避免抖动连发。
- 修饰键：合成 KeyEvent 携带 `metaState`；Framebuffer 的 `repeatCount`、Shift/Ctrl 特例按其现有语义对齐。
- 多键输出：同一逻辑按钮映射到多键时，按顺序派发 down，抬起逆序 up（保证组合键如 Ctrl+Z 稳定）。

## 4. 数据契约

### 4.1 按键方案（profile）JSON v1

存储为独立文件：`filesDir/input/profiles/<id>.json`。**无内置预置 assets**——出厂默认由代码
生成（`PadProfile.defaultProfile()`），`default` 为内置方案 id（可编辑、不可删除）。

字段以 `PadProfile.toJson` 为准，为**扁平结构**（无 `style`/`base`/`events` 嵌套；草案的
`w/h/ref/样式内联` 结构未实施）。真实样例（出厂默认方案的序列化输出）：

```json
{
  "schema": 1,
  "id": "default",
  "name": "Default",
  "direction": {
    "x": 0.17, "y": 0.8, "size": 0.3, "eightDir": true,
    "up": [19], "down": [20], "left": [21], "right": [22]
  },
  "buttons": [
    { "id": "ok", "text": "OK", "x": 0.93, "y": 0.5, "size": 0.115, "aspect": 0.46, "shape": "round", "keys": [66, 62] },
    { "id": "skip", "text": "Skip", "x": 0.93, "y": 0.67, "size": 0.115, "aspect": 0.46, "shape": "round", "keys": [113], "autoKeep": true }
  ]
}
```

（其余按钮同构：cancel/pageup/pagedown/tab 与 QWZX 圆形四键；字段按上面按钮的形状展开。）

约定：

- `x/y` 为按钮中心归一化坐标（0..1，允许 -0.1..1.1 出界摆放，与现有 `__touch_pad.js` 一致）；
  `size` 为按钮宽度相对 `min(视口宽, 视口高)` 的比例，高度 = 宽度 × `aspect`（默认 0.46，圆形键为 1）。
- `shape ∈ {round, square}`；`visible` 仅在 false 时写出（缺省 = 可见）；`keys[]` 为 canonical
  键位（Android keycode；鼠标段见 §3.2）；`autoKeep: true` 表示按下后保持（再点一次释放），
  用于 Ctrl 跳过、蓄力等。
- 解析侧防御上限（正常编辑远不会触及，坏文件/构造文件会被截断而不是撑爆内存）：
  按钮数 ≤ `MAX_PAD_BUTTONS`（128）、单个绑定键位数 ≤ `MAX_KEYS_PER_BINDING`（128）。
- 按键集合不再固定：用户可增删任意按钮、复制（副本偏移 2%）。
- 样式内联在按钮上（v1 不做具名共享样式与颜色/圆角编辑；结构预留，后续可加顶层 `styles` + 引用）。
- 控件组（FCL 的 ViewGroup）v1 不做，模型上预留 `group` 字段。

### 4.2 手柄映射 JSON v1

存储：`filesDir/input/gamepad_map.json`（全局一份；每游戏覆盖 v1 用同一个文件不区分，后续需要时加 per-game 键）。

字段以 `GamepadMap.toJson` 为准。**逻辑按键只有 16 个**（`GamepadButtons.ALL`），键名无
`stick`（单数）/`triggers` 字段——扳机/摇杆阈值是 `InputRouter` 的常量（扳机 0.5、HAT 0.85），
**不可在 JSON 中配置**。键值一律为 **Android keycode**（如 B→Esc = 111、D-Pad = 19..22；
草案样例里的 27/38/40 等是浏览器 keyCode，属笔误）。真实样例（出厂默认的序列化输出）：

```json
{
  "schema": 1,
  "buttons": {
    "A":      { "keys": [66, 62] },
    "B":      { "keys": [111] },
    "X":      { "keys": [113], "autoKeep": true },
    "Y":      { "keys": [59] },
    "START":  { "keys": [111] },
    "SELECT": { "keys": [61] },
    "L1":     { "keys": [92] },
    "R1":     { "keys": [93] },
    "L2":     { "keys": [1000] },
    "R2":     { "keys": [1001] },
    "L3":     { "keys": [113], "autoKeep": true },
    "R3":     { "keys": [59], "autoKeep": true },
    "DPAD_UP":    { "keys": [19] },
    "DPAD_DOWN":  { "keys": [20] },
    "DPAD_LEFT":  { "keys": [21] },
    "DPAD_RIGHT": { "keys": [22] }
  },
  "sticks": {
    "left":  { "up": [19], "down": [20], "left": [21], "right": [22], "deadzone": 0.35, "hysteresis": 0.05 },
    "right": { "up": [], "down": [], "left": [], "right": [], "deadzone": 0.35, "hysteresis": 0.05 }
  }
}
```

约定：

- 逻辑输入集固定枚举（上表 16 键 + 左右摇杆 4 方向仿真），与 FCL 20 项对齐（我们省去
  DIRECTION_* 独立项，摇杆方向直接由 `sticks` 配置表达）。
- `autoKeep` 即 FCL 的 toggle 语义；`keys[]` 多键输出与虚拟按键一致，共用派发器；
  单绑定键位数同样受 `MAX_KEYS_PER_BINDING`（128）约束。
- XInput 设备（`SOURCE_GAMEPAD`）与摇杆设备（`SOURCE_JOYSTICK`）统一归一；HAT 轴阈值 0.85、
  扳机 0.5 为 `InputRouter` 常量，不可配。
- 出厂默认只有**一套 Web 语义**的映射（`GamepadMap.default()`：A→Enter+Space、B→Esc、
  X→Ctrl(autoKeep)、Y→Shift、START→Esc、SELECT→Tab、L1→PageUp、R1→PageDown、L2→鼠标左、
  R2→鼠标右、L3→Ctrl(autoKeep)、R3→Shift(autoKeep)、D-Pad/左摇杆→方向键）。
  **按引擎家族分档的默认预设（KRKR/Siglus 系、Framebuffer 系）未实现**（规划）。

### 4.3 存储与并发

| 数据 | 位置 | 写者 | 读者 |
|---|---|---|---|
| 方案文件 | `filesDir/input/profiles/*.json` | app（设置页）、engine（游戏内编辑保存） | 双方 |
| 手柄映射 | `filesDir/input/gamepad_map.json` | app | 双方 |
| 每游戏选择/开关 | `tyranor_game_overrides` blob 新键（见 4.4） | app（引擎不再写 prefs） | engine 启动时读 |

- 写入一律"临时文件 + rename"原子替换；约定单写者：游戏运行期间由 engine 写方案文件，app 设置页在游戏未运行时可写，app 前台恢复时重读文件刷新列表。
- 引擎侧不再有 `TouchPadSaveBridge` 这类 prefs 回写，跨进程 prefs 限制点随之消除。

### 4.4 新键（三处字面量锚定，沿用现有约定）

`GameOverridePartitions` + `PerGameSettingsStore.F_*` + engine 侧常量：

- `input_profile_id`（String，默认 `"default"`）
- `input_pad_enabled`（Boolean，**无全局默认**：未显式设置时按引擎分档，
  MV/MZ 为 true、Tyrano/VN/WebOther 为 false）
- `input_gamepad_enabled`（Boolean，默认 true）
- `input_legacy_migrated`（Boolean，旧触屏手柄的一次性迁移标记，仅 app 侧读写）
  以上四个键在 `GameOverridePartitions.TYRANO_KEYS` 中显式建模，避免收紧分区时丢键。

### 4.5 旧配置迁移

1. 首次加载时读旧 `touch_pad_config` / `touch_pad_presets`（仍在 blob 中），按已知按钮 id 表（pageup/pagedown/tab/alt/ctrl/shift/space/enter/esc/qwzx/joystick/dpad）生成 `profiles/migrated-*.json`：以出厂默认布局为底、按旧条目覆盖位置与显隐（旧配置是「相对出厂布局的增量」）；canonical 键位取默认布局的 keyCodes 表；`x/y` 直接沿用（已是归一化）；旧 `scale` 与新 `size` 语义不同（旧相对 padSize、新相对 `min(视口边)`），**不换算**，尺寸回落新默认。
2. 原 `presets` 每个转为一个方案文件，名称保留。
3. 迁移完成后把该游戏的方案选择写进**单游戏覆盖**（`setGameProfileIdOverride`，不动全局
   `input_profile_id`——沿用内置 `default` 并改全局选择会污染其它未配置游戏）；旧键
   **永不清理**（保留为数据留底，迁移幂等性由 `input_legacy_migrated` 一次性标记承担）。

### 4.6 LaunchContract

v1 无新增 extras：引擎宿主启动时直接读文件 + blob（沿用现有 `getSharedPreferences(EnginePrefs.GAME_OVERRIDES_PREFS)` 读取模式）。若后续需要由 app 强制下发（如首次引导直接进入编辑模式），再按需加 extras 常量。

## 5. engine 侧实现

新增包 `engine/src/main/java/com/core/input/`：

- `CanonicalKeys.kt`：键位常量、鼠标段、动作段。
- `InputRouter.kt`：手柄事件归一（KeyEvent/MotionEvent → 逻辑输入）、摇杆方向状态机、映射查找、多键派发、消费策略；宿主在 `dispatchKeyEvent`/`dispatchGenericMotionEvent` 最前调用。
- `InputSink.kt`：`fun send(key: Int, down: Boolean)` 接口 + 各宿主实现（小类，按 §3.3 表；当前只有 Web 系的 `InputRemapController` 装配，见下）。
- `PadProfile.kt` / `GamepadMap.kt`：JSON 解析（org.json，无新依赖）、默认值、序列化。
- `InputConfigStore.kt`：方案/映射文件读写（临时文件 + rename 原子替换、备份式回滚）与生效设置解析（单游戏覆盖 ?: 全局显式 ?: 引擎默认）。
- `WebKeyCodes.kt`：Android keycode → 浏览器 keyCode 表（纯函数）。
- `InputJsonLimits.kt`：解析约束（schema 兼容判定、`MAX_PAD_BUTTONS`、`MAX_KEYS_PER_BINDING`）。
- `InputRemapController.kt`：Web 宿主装配（`installWeb`，Tyrano/RpgMaker 两处入口）。
- `VirtualPadView.kt`：自绘覆盖层 View（参考现有 `VirtualMouseLayer` 形态，无 Compose）：
  - 渲染：按钮/方向控件/样式；`layout()` 全视口锚定 + resize/rotation 重排（沿用现有归一化策略）。
  - 触摸：按下/抬起/长按/双击识别、多指、滑动联动（可选）、按住保持（autoKeep）。
  - 编辑模式：选中（描边高亮）、拖拽、缩放（手柄/滑条）、悬浮编辑栏（设置/复制/删除）、属性对话框（文本/尺寸/按下保持/显隐/八向）、键位网格对话框（canonical 键多选 + 鼠标区）、保存/取消（工作副本草稿模型）。**无位置数值输入与颜色/圆角/样式编辑**（草案中的位置/样式编辑未实施）。
  - 入口：可拖动原生 FAB（位置持久化于 `tyranor_input` prefs）；**点按切换按键层显隐，长按进入编辑模式**；**app 侧暂无可关闭 FAB 的设置**（规划）。
- FAB/编辑态与现有手势：编辑态全吞输入并拦截冒泡（沿用 JS 版经验：遮罩层 + stopPropagation 等价物——native 层直接消费事件）。
- 与 `VirtualMouseLayer` 协调：两者可共存（pad 只消费自己命中的区域）；鼠标码输出优先复用 `__tnMouse`（Web）与宿主鼠标 API（KRKR 触摸），其余宿主 v1 打日志降级。
- 顺带统一：两处 `VirtualMouseLayer.kt` 副本（`com.core.tyrano` / `com.core.rpgmaker`，内容已漂移）合并为 `com.core.input` 或共享实现。

## 6. app 侧实现

- `core/input/InputRemapRepository.kt`：方案/映射/开关的 app 侧读写门面 + 旧数据迁移器 + 键位目录。
  **无内置预置解包（assets）**——出厂默认由 engine 侧代码生成。
- 手柄映射读写无独立 Store：经 `InputRemapRepository` ↔ engine 侧 `InputConfigStore`（同一 filesDir）。
- `core/settings`：新增 4.4 四个覆盖键（含 `input_legacy_migrated`）；`PerGameSettingsStore` 镜像同步（沿用现有 F_* 模式）。
- `ui/settings/InputSettingsScreen.kt`：
  - 方案管理：列表、选择、复制、重命名、删除、导入/导出、整页进入布局编辑器（`PadLayoutEditActivity`，编辑即所见即所得）；**无独立预览画布**（草案的「手机比例画布 + 触控仿真」未实施）。
  - 手柄映射（`GamepadMapScreen.kt`）：键位网格多选对话框逐逻辑按键/摇杆方向编辑 + 恢复默认；**无设备列表、无物理按键捕获、无冲突提示**（草案的「捕获式绑定」未实施）。
  - 开关：虚拟按键启用、手柄映射启用（全局默认 + 每游戏覆盖）。
- 文案：新增 string 资源（zh/en/ja 三套，跟随现有规范）。

## 8. 风险与边界

- 外置 APK 引擎不可覆盖（见 §1）。
- SurfaceView 类引擎的视频覆盖层（ONS `OnsIjkVideoView`、Artemis `VideoViewActivity` 用 `setZOrderOnTop`）会盖住按键层，视频播放期间需隐藏或处理。
- Web 引擎输出回退 JS 合成：`evaluateJavascript` 频率无压力（按键事件低频），但需保证 JS 接收器在页面早期注入（沿用 `</body>` 注入通道）。
- 文本输入期（KRKR `KrInputConnection`、Siglus IME）必须放行，否则影响游戏内命名输入。
- 各宿主真机回归面大（8 个宿主）；Framebuffer 键集有限（无 Alt/部分字母走 `fbText`），方案里对应按钮需按引擎裁剪默认键位。
- 跨进程文件并发：原子替换 + 单写者约定（游戏运行期 engine 写、否则 app 写），app 前台恢复重读。
- 编辑态与游戏输入的冲突：编辑态全吞，仅编辑栏/选中控件可交互（与 JS 版一致的策略，native 实现更可靠）。
