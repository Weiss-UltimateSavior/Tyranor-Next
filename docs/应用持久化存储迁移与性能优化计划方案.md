# TyranorNext 应用持久化存储迁移与性能优化计划方案

> 生成日期：2026-08-29  
> 基于文档：`docs/应用持久化数据清单.md`  
> 目标：在不破坏现有用户数据、引擎跨进程读取契约和备份行为的前提下，将高频集合型数据从 SharedPreferences / 自定义文本迁移到更适合的存储技术栈，提升游戏页、首页、封面刷新、目录同步和搜索排序性能。

---

## 一、结论先行

当前项目最需要优化的不是“所有持久化都迁 SQLite”，而是把**高频读写、集合型、需要查询/排序/局部更新的数据**迁到 Room/SQLite。

推荐最终技术栈：

| 数据类型 | 推荐技术 | 原因 |
|---|---|---|
| 游戏库主数据、扫描根、最近游戏、快捷启动、封面元数据、引擎识别缓存 | Room + SQLite | 支持索引、事务、局部更新、Flow 订阅、批量写入和一致性约束 |
| Hikarinagi OAuth token | EncryptedSharedPreferences / Android Keystore | 这是安全问题，不是性能问题；token 不适合普通明文 prefs |
| App 外观、语言、主题、少量开关 | 保留 SharedPreferences，后续可迁 Preference DataStore | 数据量小，读写频率低，迁 SQLite 收益小 |
| 引擎全局设置、native 插件安装状态、跨进程少量配置 | 暂保留 SharedPreferences | 引擎子进程直接读取，迁 DB 会增加跨进程初始化和兼容成本 |
| 封面图片、字体、native so、存档、SAF 影子目录、patch overlay | 保留文件系统 | 二进制大文件不适合进 DB，DB 只存索引和元数据 |

优先级排序：

1. P0：迁移 `game_scanner.xml` 中的游戏库、扫描根、最近游戏、快捷启动。
2. P0：封面元数据从 `ScanGame` 整列表重写改为 DB 单行更新。
3. P1：单游戏覆盖设置从 `tyranor_game_overrides.xml` 的 JSON-in-XML 迁到 Room 表或兼容型 Repository。
4. P1：Artemis / Ren'Py / RPGM 自动识别缓存统一进 DB。
5. P2：Hikarinagi token 改加密存储。
6. P3：App 设置可选迁 DataStore，不作为性能优先项。

## 二、当前瓶颈分析

### 2.1 游戏库主数据瓶颈

当前核心实现位于：

- `app/src/main/java/com/tyranor/next/core/game/scan/EngineScanner.kt`

现状：

- `scan_games`：所有游戏记录被序列化成一个字符串。
- 每行一条游戏，字段用 `\u0001` 分隔。
- `loadGames()` 需要读取整串、split、逐行 parse。
- `updateGames()` 即使只改一个游戏封面，也会重写整个 `scan_games`。
- `recent_games`、`quick_launch` 也重复保存完整 `ScanGame` 快照。

问题：

- 游戏数量变多后，冷启动和页面切换需要反复构造大列表。
- 封面刮削“获取到一个刷新一个”会触发多次整库重写。
- 删除目录、删除游戏、最近游戏、快捷启动之间需要手动保持一致，逻辑越来越绕。
- 搜索和排序只能在内存列表上做，无法利用索引。
- 自定义分隔符格式脆弱，字段扩展需要维护 parse 兼容。

### 2.2 单游戏覆盖设置瓶颈

当前核心实现位于：

- `app/src/main/java/com/tyranor/next/core/settings/PerGameSettingsStore.kt`
- `engine/src/main/java/com/core/tyrano/TyranoActivity.kt`

现状：

- 每个游戏以 `game.uri` 为 key。
- value 是 JSON 字符串。
- 缺失字段表示跟随全局。
- Tyrano 引擎进程中也会直读同一个 prefs 文件保存触控板配置。

问题：

- 数据结构越来越大，KR / Artemis / ONS / RPGM / Ren'Py / TouchPad 混在同一个 JSON。
- 每次改一个字段都要读取并写回整段 JSON。
- 迁移要小心，因为引擎侧已有直接读取契约。

### 2.3 封面与元数据瓶颈

当前文件：

- `app/src/main/java/com/tyranor/next/core/cover/CoverScrapeTaskManager.kt`
- `app/src/main/java/com/tyranor/next/core/cover/CoverScraperService.kt`
- `app/src/main/java/com/tyranor/next/core/cover/VndbCoverService.kt`

现状：

- 图片二进制保存在 `files/covers_remote/`。
- 元数据写回 `ScanGame.coverUri / coverSource / vndbId / metadataTitle`。
- 写回路径仍走 `EngineScanner.updateGames()`。

问题：

- 封面文件存储方式没问题。
- 真正低效的是封面元数据更新，一个游戏封面改变会牵动整库字符串。

### 2.4 自动引擎识别缓存分散

当前散落位置：

- `EngineLauncher.kt` 中 Artemis 版本记忆：
  - `artemis_engine.<pathHash>`
  - `artemis_engine_success.<pathHash>`
- `ScanGame.detectedRenpyVersion`
- `ScanGame.externalModuleAlias`

问题：

- 自动识别结果和游戏库、启动成功历史、特征 hash 没有统一模型。
- 后续新增 mkxp-z、Ren'Py 多版本、RPGM 模块版本时，prefs key 会继续膨胀。

## 三、迁移目标

### 3.1 性能目标

- 游戏页冷加载不再解析整段 `scan_games` 文本。
- 改一个封面只更新一行 DB。
- 删除一个目录能事务性删除目录下所有游戏、最近记录、快捷启动记录。
- 搜索、排序、按引擎筛选可走 SQL 索引。
- 首页和游戏页通过同一数据源订阅，减少手动同步。

### 3.2 稳定性目标

- 首次升级自动从旧 SharedPreferences 导入数据。
- 导入成功后保留旧数据至少一个版本，便于回滚。
- 不改变现有游戏目录、存档目录、封面文件、字体文件位置。
- 不影响引擎子进程读取必要配置。
- 不要求用户重新扫描目录。

### 3.3 架构目标

新增一层 Repository，让 UI 不直接依赖 `EngineScanner` 的存储实现：

```text
UI / ViewModel
└── GameLibraryRepository
    ├── Room DAO
    ├── Legacy SharedPreferences Importer
    └── EngineScanner 扫描识别逻辑
```

`EngineScanner` 后续保留“扫描/识别”职责，逐步剥离“持久化仓库”职责。

## 四、推荐数据库设计

### 4.1 `games`：游戏库主表

用途：替代 `game_scanner.xml` 中的 `scan_games`。

字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `uri` | TEXT PRIMARY KEY | 游戏唯一标识，沿用现有 `ScanGame.uri` |
| `root_uri` | TEXT | 所属扫描根，用于删除目录时批量清理 |
| `title` | TEXT NOT NULL | 展示标题 |
| `engine` | TEXT NOT NULL | `EngineType.name` |
| `launch_target` | TEXT NOT NULL DEFAULT '' | 自动识别的启动目标 |
| `launch_file` | TEXT NULL | 用户手动指定启动文件 |
| `cover_uri` | TEXT NULL | 封面 URI |
| `cover_source` | TEXT NULL | local/custom/vndb/steam/bangumi/hikarinagi |
| `vndb_id` | TEXT NULL | VNDB ID |
| `metadata_title` | TEXT NULL | 元数据标题 |
| `external_module_alias` | TEXT NULL | 外置 APK 子运行时别名 |
| `detected_renpy_version` | TEXT NULL | 扫描阶段 Ren'Py 版本建议 |
| `discovered_at` | INTEGER NOT NULL | 首次发现时间 |
| `updated_at` | INTEGER NOT NULL | 最近修改时间 |
| `last_opened_at` | INTEGER NOT NULL DEFAULT 0 | 最近打开时间，可替代 recent 快照 |

索引建议：

```sql
CREATE INDEX index_games_root_uri ON games(root_uri);
CREATE INDEX index_games_engine ON games(engine);
CREATE INDEX index_games_title ON games(title COLLATE NOCASE);
CREATE INDEX index_games_last_opened_at ON games(last_opened_at);
CREATE INDEX index_games_cover_uri ON games(cover_uri);
```

收益：

- `replaceGame()` 可变成单行 `UPDATE`。
- 搜索标题可加速。
- 删除扫描根时可以按 `root_uri` 批量删除。
- 最近游戏可以直接从 `games.last_opened_at` 查询。

### 4.2 `scan_roots`：扫描根目录表

用途：替代 `scan_roots` 换行字符串。

字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `uri` | TEXT PRIMARY KEY | SAF tree URI 或真实路径 |
| `display_name` | TEXT NULL | 展示名，可缓存 |
| `added_at` | INTEGER NOT NULL | 添加时间 |
| `scan_depth` | INTEGER NULL | 预留：单目录扫描深度覆盖 |
| `last_scanned_at` | INTEGER NOT NULL DEFAULT 0 | 最近扫描时间 |

收益：

- 设置页目录列表可直接订阅。
- 添加/删除目录和游戏库清理可放在同一事务。

### 4.3 `quick_launch`：快捷启动表

用途：替代 `quick_launch` 完整游戏快照。

字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `game_uri` | TEXT PRIMARY KEY | 指向 `games.uri` |
| `slot_index` | INTEGER NOT NULL | 0..2 |
| `updated_at` | INTEGER NOT NULL | 更新时间 |

约束建议：

- `FOREIGN KEY(game_uri) REFERENCES games(uri) ON DELETE CASCADE`
- `UNIQUE(slot_index)`

收益：

- 游戏标题/封面变更后，快捷启动不需要同步快照。
- 删除游戏时快捷启动自动清理。

### 4.4 `game_overrides`：单游戏覆盖表

用途：替代或兼容 `tyranor_game_overrides.xml`。

第一阶段建议不要一次性拆成几十列，先用结构化 JSON 分区，减少迁移风险：

| 字段 | 类型 | 说明 |
|---|---|---|
| `game_uri` | TEXT PRIMARY KEY | 游戏 ID |
| `kr_json` | TEXT NULL | KR 覆盖 |
| `artemis_json` | TEXT NULL | Artemis 覆盖 |
| `ons_json` | TEXT NULL | ONS 覆盖 |
| `tyrano_json` | TEXT NULL | Tyrano / RPGM 覆盖 |
| `renpy_json` | TEXT NULL | Ren'Py 覆盖 |
| `touchpad_json` | TEXT NULL | 触控板配置 |
| `updated_at` | INTEGER NOT NULL | 更新时间 |

第二阶段再评估是否拆列：

- 高频筛选字段拆列。
- 低频配置继续 JSON。

注意：

- Tyrano 引擎进程目前会直接读写 `tyranor_game_overrides.xml`。
- 因此第一阶段建议 App 层先迁库，但保留 prefs 镜像写回。
- 等引擎侧改为通过统一 bridge/repository 读取后，再完全移除旧 prefs。

### 4.5 `engine_detection_cache`：自动引擎识别缓存表

用途：统一 Artemis / Ren'Py / RPGM / mkxp-z 等自动识别结果。

字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `game_uri` | TEXT PRIMARY KEY | 游戏 ID |
| `engine` | TEXT NOT NULL | 引擎类型 |
| `fingerprint_hash` | TEXT NULL | 特征 hash，用于判断缓存是否过期 |
| `artemis_version` | TEXT NULL | 自动判定的 Artemis 版本 |
| `artemis_success_version` | TEXT NULL | 最近成功启动版本 |
| `renpy_version` | TEXT NULL | 自动判定 Ren'Py 版本 |
| `rpgm_runtime` | TEXT NULL | RPGM 子运行时 |
| `mkxpz_supported` | INTEGER NULL | mkxp-z 支持判断 |
| `confidence` | INTEGER NOT NULL DEFAULT 0 | 置信度 |
| `reason` | TEXT NULL | 识别原因，便于日志/详情展示 |
| `updated_at` | INTEGER NOT NULL | 更新时间 |

收益：

- 自动引擎项可以有更稳定的“记忆 + 特征失效”逻辑。
- 后续排查用户日志时能输出命中的识别原因。

### 4.6 `cover_jobs` / `cover_candidates`：封面刮削可选增强

这不是第一阶段必须项，但适合后续增强。

`cover_candidates` 可保存多个候选：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | 候选 ID |
| `game_uri` | TEXT NOT NULL | 游戏 ID |
| `source` | TEXT NOT NULL | 来源 |
| `remote_id` | TEXT NULL | VNDB/Steam/Bangumi/Hikarinagi ID |
| `title` | TEXT NULL | 候选标题 |
| `image_url` | TEXT NULL | 远程图片 URL |
| `score` | REAL NOT NULL DEFAULT 0 | 匹配分 |
| `created_at` | INTEGER NOT NULL | 创建时间 |

收益：

- 支持“选择其他候选封面”。
- 避免重复请求同一候选。

## 五、哪些不建议迁 SQLite

### 5.1 全局 App 设置

文件：

- `app_settings.xml`

包括：

- 主题色
- 语言
- 主题模式
- 色调切换
- 扫描深度
- 游戏排序
- 封面源开关与顺序

建议：

- 暂保留 SharedPreferences。
- 如果想现代化，可迁 Preference DataStore。
- 不建议迁 SQLite，因为数据小、键值型、查询需求弱。

### 5.2 全局引擎设置

文件：

- `yukihub_prefs.xml`
- `onsyuri.xml`

建议：

- 暂保留 SharedPreferences。
- 原因是引擎子进程和 vendored 引擎代码可能直接读 prefs。
- SQLite 跨进程读写虽然可行，但要处理初始化、锁、事务和生命周期，收益不如风险。

### 5.3 native 插件安装状态

文件：

- `rinne_native_plugin_overrides.xml`
- `yukihub_prefs.xml` 中 `native_plugin.*`

建议：

- 保留 SharedPreferences。
- 安装状态是少量键，且启动早期要快速读取。
- 插件实体 `.so` 和 `manifest.json` 继续放文件系统。

### 5.4 二进制和大文件

包括：

- 封面图片
- 字体
- native so
- 存档
- SAF shadow tree
- `patch.tjs` overlay
- zip 临时文件

建议：

- 全部保留文件系统。
- SQLite 只保存路径、hash、mtime、来源等索引。

## 六、迁移路线

### 阶段 0：准备与保护

目标：在不改变现有行为的情况下加入基础设施。

任务：

1. 引入 Room 依赖。
2. 新增 `AppDatabase`。
3. 新增 Entity / DAO。
4. 新增 `GameLibraryRepository`。
5. 新增 legacy importer，从旧 prefs 导入 DB。
6. 增加迁移完成标记，例如 `storage_migration_v1_done`。
7. 保留旧 prefs 原始数据，不立即删除。

验收：

- Debug / Release 均可编译。
- 新安装用户 DB 为空时不崩。
- 老用户首次启动可从旧数据导入。
- 导入重复执行幂等。

### 阶段 1：迁移游戏库主数据

目标：替换 `scan_games` / `scan_roots` / `recent_games` / `quick_launch`。

任务：

1. `scan_roots` 导入 `scan_roots` 表。
2. `scan_games` 导入 `games` 表。
3. `recent_games` 的 `openTime` 合并到 `games.last_opened_at`。
4. `quick_launch` 导入 `quick_launch` 表，只保存 `game_uri + slot_index`。
5. `EngineScanner.saveGames/loadGames/updateGames` 改为调用 Repository 或 DAO。
6. 保持旧接口签名，降低 UI 改动范围。
7. `MainLibraryViewModel` 的发布快照改为从 Repository 读。

验收：

- 添加目录、删除目录、扫描、增量扫描、删除游戏正常。
- 首页最近游戏和快捷启动与游戏页一致。
- 封面更新后快捷启动同步显示新封面。
- 不需要用户重新添加目录。

### 阶段 2：封面元数据局部更新

目标：封面刮削不再重写整库。

任务：

1. 新增 DAO 方法：
   - `updateCover(gameUri, coverUri, coverSource, vndbId, metadataTitle, updatedAt)`
   - `clearCover(gameUri)`
2. `CoverScrapeTaskManager.persistScrapedCover()` 改成单行事务更新。
3. `VndbCoverService` 手动换封面走同一 Repository。
4. `MainLibraryViewModel` 订阅 DB Flow，减少手动 `MutableSharedFlow` 同步压力。

验收：

- 一键获取封面时，获取到一个刷新一个。
- 游戏列表不需要滑动才刷新。
- 批量刮削时不会频繁重写巨大 prefs 字符串。

### 阶段 3：搜索与排序优化

目标：游戏页搜索速度和大列表切换性能提升。

任务：

1. DAO 增加查询：
   - `observeGames(sortMode)`
   - `searchGames(query, sortMode)`
   - `observeGamesByEngine(engine)`
2. 标题搜索使用 `LIKE '%' || :query || '%' COLLATE NOCASE`。
3. 如果后续游戏量很大，可引入 SQLite FTS5：
   - `games_fts(title, metadata_title)`
4. 排序策略：
   - 默认标题排序走 `title COLLATE NOCASE`。
   - 标签分组可增加 `sort_tag` 预计算列，避免 UI 每次 regex。

验收：

- 搜索输入时不卡顿。
- 大量游戏下页面切换不重新构造无关列表。
- 排序切换后结果稳定。

### 阶段 4：单游戏覆盖设置迁移

目标：将 `tyranor_game_overrides.xml` 从 JSON-in-XML 迁为 DB 管理，同时保持引擎兼容。

推荐过渡策略：

```text
App UI 写入 DB
      ↓
Repository 同步写一份旧 prefs 镜像
      ↓
引擎进程仍按旧方式读取
```

任务：

1. 导入旧 `tyranor_game_overrides.xml` 到 `game_overrides` 表。
2. App 侧 `PerGameSettingsStore` 改成 Repository facade。
3. 每次 App 修改覆盖设置时：
   - 写 DB。
   - 同步生成旧 JSON 到 prefs，供引擎子进程读。
4. Tyrano `TouchPadSaveBridge` 暂不迁，继续写旧 prefs。
5. App 启动时检测旧 prefs 中 touchpad 配置是否新于 DB，必要时回灌。

验收：

- 单游戏设置页显示正确。
- KR / Artemis / ONS / RPGM / Ren'Py 覆盖仍生效。
- Tyrano 触控板布局保存不丢。
- 引擎进程不需要一次性大改。

### 阶段 5：自动引擎识别缓存迁移

目标：统一自动引擎版本识别结果。

任务：

1. 新增 `EngineDetectionRepository`。
2. Artemis 成功启动版本从 prefs 迁到 `engine_detection_cache`。
3. Ren'Py 扫描版本建议写入 `engine_detection_cache`。
4. mkxp-z / RPGM 外置模块识别结果写入同表。
5. 增加 fingerprint hash：
   - 关键文件名列表 hash。
   - 关键配置文件 mtime/size。
6. fingerprint 变化时自动重新识别。

验收：

- 自动引擎项能解释“为什么选这个版本”。
- 游戏升级/文件变化后缓存自动失效。
- 旧 prefs 版本记忆可导入。

### 阶段 6：敏感数据加密

目标：处理 `hikarinagi_auth.xml` 明文 token 风险。

任务：

1. 引入 AndroidX Security Crypto。
2. 新建 `SecureAuthStore`。
3. 首次启动把旧 token 从 `hikarinagi_auth.xml` 迁到加密 prefs。
4. 迁移成功后清空旧 token 字段。
5. 继续保持备份规则排除 auth 文件。

验收：

- 旧用户登录状态不丢。
- 登出/刷新 token 正常。
- 备份不包含 token 明文。

## 七、Room 依赖建议

`gradle/libs.versions.toml`：

```toml
[versions]
room = "2.8.0"

[libraries]
androidx-room-runtime = { module = "androidx.room:room-runtime", version.ref = "room" }
androidx-room-ktx = { module = "androidx.room:room-ktx", version.ref = "room" }
androidx-room-compiler = { module = "androidx.room:room-compiler", version.ref = "room" }

[plugins]
ksp = { id = "com.google.devtools.ksp", version = "2.3.20-2.0.0" }
```

`app/build.gradle.kts`：

```kotlin
plugins {
    alias(libs.plugins.ksp)
}

dependencies {
```

## 九、数据迁移策略

### 9.1 导入顺序

首次启动执行：

1. 读取旧 `scan_roots`。
2. 导入 `scan_roots` 表。
3. 读取旧 `scan_games`。
4. 根据 `root_uri` 归属写入 `games` 表。
5. 读取旧 `recent_games`，合并 `openTime` 到 `games.last_opened_at`。
6. 读取旧 `quick_launch`，按原顺序写入 `quick_launch.slot_index`。
7. 读取旧 `tyranor_game_overrides`，写入 `game_overrides` 表。
8. 读取旧 Artemis 自动版本 prefs，写入 `engine_detection_cache`。
9. 写入迁移完成标记。

### 9.2 幂等要求

迁移必须满足：

- 可重复执行。
- 不重复插入。
- 不覆盖 DB 中更新的封面和标题。
- 如果旧数据 parse 失败，只跳过单条，不中断全局迁移。

### 9.3 回滚策略

至少一个版本内：

- 不删除旧 `game_scanner.xml`。
- 不删除旧 `tyranor_game_overrides.xml`。
- App 层继续可从旧 prefs 重新导入。

如果 DB 初始化失败：

- fallback 到旧 `EngineScanner` prefs 实现。
- 记录日志。
- 不影响用户启动游戏。

## 十、备份策略调整

迁 Room 后需要更新：

- `app/src/main/res/xml/backup_rules.xml`
- `app/src/main/res/xml/data_extraction_rules.xml`

建议：

| 数据 | 是否备份 | 原因 |
|---|---|---|
| Room 游戏库 DB | 是 | 用户游戏库、封面元数据、设置迁移后需要保留 |
| Room WAL/SHM | 否/可排除 | 可重建，避免备份不一致 |
| auth 加密 prefs | 否 | token 不应备份 |
| `noBackupFilesDir/krkr_saf_index` | 否 | SAF 权限恢复后可能失效，本来就在 noBackup |
| cache | 否 | 可重建 |

注意：

- SAF URI 权限不能靠云备份恢复。
- 恢复到新设备后，扫描根可能需要重新授权。
- DB 中应标记 root 授权状态，UI 可以提示“目录需要重新授权”。

## 十一、性能收益预估

### 当前模型

```text
更新一个封面
→ load scan_games 整串
→ split 全部游戏
→ parse 全部游戏
→ map 全部游戏
→ serialize 全部游戏
→ 写回 SharedPreferences XML
```

### 迁移后模型

```text
更新一个封面
→ UPDATE games SET cover_uri=?, cover_source=? WHERE uri=?
→ Room Flow 推送变更
→ UI 单项刷新
```

预期收益：

- 游戏数量越多，收益越明显。
- 封面批量刮削期间磁盘写入量显著下降。
- 删除目录/删除游戏同步逻辑更简单。
- 搜索排序从 O(n) 内存处理变为可索引 SQL 查询。

---

## 十二、风险点与规避

| 风险 | 说明 | 规避 |
|---|---|---|
| Room 引入后构建链路变复杂 | 需要 KSP/kapt | 先单独提交依赖和空 DB 验证 Debug/Release |
| 旧数据迁移漏字段 | `ScanGame` 字段持续增加 | 写 migration 单测，覆盖旧行式格式 |
| 引擎子进程读不到单游戏覆盖 | 引擎目前直读 prefs | 第一阶段保留 prefs 镜像写回 |
| DB 与旧 prefs 双写不一致 | 过渡期常见问题 | 以 DB 为主，prefs 为引擎兼容输出 |
| SAF root 归属判断复杂 | content uri 和真实路径并存 | 复用 `EngineScanner.isGameUnderRoot` 逻辑，迁移时保存 root_uri |
| 用户回滚版本 | 新版写 DB，旧版读 prefs | 至少一个版本内继续写旧 prefs 的关键字段 |

## 十五、最终推荐实施路径

最推荐从 P0 开始：


单游戏覆盖设置和 token 加密可以后续独立做，避免一次 PR 同时碰 UI、扫描、引擎进程和安全存储，导致问题难定位。
