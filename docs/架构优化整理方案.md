## 1. 总体判断

三层架构（`ui → core → engine`）方向正确，依赖方向的"硬规则"已守住，但存在两处结构性弱点：

1. **core 层内部职责失控**——God Object 集中、错误协议碎片化、违反自身声明的依赖约束；
2. **ui 层 ViewModel 缺位**——仅 1 个 VM，页面状态散落 composable，巨型文件寄生组件造成横向依赖。

### 1.1 已守住的红线（无需改动）

| 红线 | 验证结果 |
| --- | --- |
| engine 不依赖 app 层（`com.tyranor.next.*`） | grep 全量 0 命中 |
| ui 不 import 引擎底层包（`com.core`/`com.akira`/`com.yuri`/`org.tvp`/`org.libsdl`/`bridge` 等） | 0 违规 |
| engine 模块依赖极简 | 仅 appcompat + documentfile + kotlin-stdlib，全 `implementation` 不传递 |
| 公共组件复用 | AppTopBar 10 处、AppAlertDialog 8 处，复用良好 |
| Activity 传参类型安全 | `ScanGameIntents` 工厂模式统一 |
| 写路径串行化 | 仓库层单线程 FIFO 执行器兜底 |
| 纯函数抽离可测 | 23 个 JVM 测试（StateReducer/Codec/SortKeys 等） |
| 文档纪律 | CONTEXT.md / AGENT.md 与代码大体一致，契约意识强（注释记录 issue #74、ABI 兼容等） |

## 2. 问题清单

优先级定义：
- **P0** 结构性缺陷，持续增加维护成本，改动收益最大；
- **P1** 局部退化（重复/寄生/越界），影响可读性与一致性；
- **P2** 隐患与卫生问题，暂不阻塞但应记录。

### 2.1 core 层（P0）

#### P0-1 EngineScanner God Object

- **位置**：`app/src/main/java/com/tyranor/next/core/game/scan/EngineScanner.kt`（1011 行）
- **现状**：object 单例持有 **27 个公共方法**，横跨至少 7 类职责：
  1. 扫描（`scanAll` / `rescanLibrary` / `incrementalScan` / `scanRoot`）
  2. 游戏库 CRUD 缓存门面（`loadGames` / `updateGames` / `updateGameCover` / `removeGame`）
  3. 最近游玩（`recordRecentGame` / `loadRecentGames` / `removeRecentGame`）
  4. 快捷启动（`loadQuickLaunch` / `addQuickLaunch` / `removeQuickLaunch` / `refreshQuickLaunch` / `isQuickLaunched`）
  5. 扫描根（`saveRoot` / `removeRoot` / `removeRootAndGames` / `loadRoots`）
  6. 引擎识别（`detectEngine` / `applyLocalCover`）
  7. URI/路径工具（`safUriToPath` / `isRemovableStoragePath` / `safeSaveName`）
- **额外耦合**：持有 3 个 `StateFlow` 修订号 + 4 组内存缓存，`init` 块（63-66 行）反向注册 `GameLibraryRepository.onPersistFailure` 回调——object 间隐式加载顺序耦合。
- **影响**：库管理职责与 `GameLibraryRepository` 重叠（同一操作有同步/挂起两套版本）；UI 组合期可直写持久层；测试必须绕开单例。
- **建议**：库 CRUD / 最近游玩 / 快捷启动 / 扫描根职责归还 `GameLibraryRepository`（或新建 `GameLibraryFacade` 门面），Scanner 只保留"扫描 + 引擎识别"；修订号广播统一为仓库层职责。

#### P0-2 EngineLauncher 硬编码全部内置引擎

- **位置**：`app/src/main/java/com/tyranor/next/core/game/launch/EngineLauncher.kt`（1269 行）
- **现状**：公共面窄（`launch` / `needsArtemisPatchConfirm` / `supportedEngines`），但 14-44 行一次性 import **13 个引擎类**（各引擎 Activity + `KrSafMirror` + `EngineSessionRegistry`）；私有函数 36 个，内部混杂各引擎 Intent 构造、patch overlay 写盘、SAF 镜像决策、参数拼装、Artemis 版本回退链。
- **影响**："功能抽象层"实际硬编码知道每一个具体引擎；外置引擎已有 `ExternalEngineModuleRegistry` 模块抽象，内置引擎未走同一条路，依赖倒置缺口最大。
- **建议**：以 `ExternalEngineModuleRegistry` 为模板，为内置引擎建立统一 `InternalEngineModule` 抽象（`canHandle(engine) + buildIntent()`），EngineLauncher 只做编排与设置合并；每引擎 Intent 构造拆为独立策略类。

#### P0-3 三级设置合并逻辑无抽象

- **位置**：`EngineLauncher.kt` 30+ 处（108-109、206-208、395-510、632-641、900-901、1255-1262）
- **现状**：应用/引擎/单游戏三级设置的覆盖合并以 `?:` 逐字段散落在 EngineLauncher 内，无统一合并器；`EngineSettingsStore`（73 个 getter/setter）与 `PerGameSettingsStore.KR_FIELDS` 字段清单重复。
- **影响**：每新增一个设置项需同步改 `EngineSettingsStore` / `PerGameSettingsStore` / `EngineLauncher` 三处，且该层零测试覆盖。
- **建议**：抽取 `EffectiveEngineSettings` 合并器（纯函数、可单测），统一 resolve 三级覆盖；EngineLauncher 只消费结果。同步收敛字段清单到单一来源。

#### P0-4 core 违反自身"不依赖 Compose"约束

- **位置**：
  - `core/settings/AppSettingsStore.kt:5-6`（4 个 `MutableState`：languageState/navStyleState/gameSortState/coverScraperSettingsVersion）
  - `core/auth/HikarinagiAuthStore.kt:5-6`（`statusVersion: MutableState<Int>`）
  - `core/cover/CoverScrapeTaskManager.kt:6-7`
  - `core/game/model/ScanGame.kt:5`（`@Immutable` 注解，灰色地带）
- **影响**：core 单例直接持有 Compose 可观察全局状态，无法脱离 Compose/主线程测试；与 AGENT.md:58 声明冲突。
- **建议**：Compose 状态改为 `StateFlow` 或纯数据载荷（`ThemeColorPayload` 模式已验证可行，UI 层订阅转换）；`@Immutable` 若保留需在 AGENT.md 明确豁免 runtime 注解。

- **已修复（2026-09-10）**：4 个 `MutableState` 与 `HikarinagiAuthStore.statusVersion` 改 `MutableStateFlow`，`CoverScrapeTaskManager.state` 改 `StateFlow`，`ScanGame` 移除 `@Immutable`；UI 全部 `collectAsState()` 订阅。core 已零 `androidx.compose.*` 依赖，AGENT.md 恢复严格禁令。

#### P0-5 core 依赖 app R 资源

- **位置**：15 个 core 文件 `import com.tyranor.next.R`（含 EngineLauncher、EngineScanner、GameSaveManager、CoverScraperService、updater 全部 4 文件）；典型如 `GameSaveManager.kt:123-160` 全部 `throw IOException(text(R.string....))`
- **影响**：core 不是独立模块，与 app 资源编译强绑定；错误消息本地化文案当异常消息用，调用方无法程序化区分错误类型。
- **建议**：core 改传 `@StringRes Int` 或错误码枚举，文案组装上移 UI 层；为 P0-6 模块化铺路。

#### P0-6 错误协议碎片化（5 种风格并存）

| # | 风格 | 代表位置 |
| --- | --- | --- |
| 1 | `runCatching → null` | 全 core 25 处调用（主流） |
| 2 | `String?` 错误码 | `EngineLauncher.launch(): String?` |
| 3 | `IOException(本地化文案)` | `GameSaveManager.kt:123-160` |
| 4 | runCatching → 日志吞掉 | `EngineLauncher.kt:476,946,991,1035` |
| 5 | sealed Result（仅新代码） | `updater/GitHubUpdateChecker.kt:170`、`UpdateApkDownloader.kt:18`、`cover/CoverScraperService.kt:38` |

- **影响**：调用方无法统一分支处理；新旧代码协议不一致。
- **建议**：以 updater/cover 已验证的 sealed Result 为模板，优先改造 `launch(): String?` 与 `GameSaveManager` 两处高频调用链；在 AGENT.md 固化错误协议选型规则。

### 2.2 ui 层（P1）

#### P1-1 ViewModel 覆盖率极低

- **现状**：全 ui 层仅 1 个 `MainLibraryViewModel`（367 行）；其余 14 个文件约 145 处 `remember { mutableStateOf }`，二级 Activity 全部直调 core 静态单例；`MainScreen.kt:88-94` 在 `LaunchedEffect` 里手动 `withContext(Dispatchers.IO)` 读设置（组合期 IO）。
- **建议**：二级 Activity 至少把 IO 调用移出组合期（VM 或 `produceState`）；不强制全量补 VM，但新页面必须走 VM。

#### P1-2 GameScreen 巨型文件 + 寄生组件

- **位置**：`ui/game/GameScreen.kt`（1655 行）
- **现状**：内嵌 ~650 行封面搜索子系统（`CoverSearchDialog:1004` / `CoverCandidateCard:1220` / `CoverBitmapCache:1599` / `CoverThumbnailLoader:1607`）及通用工具（`startActivityWithPageTransition:349` / `cleanupDeletedGame:332` / `rememberCoverBitmap:1521` / `gameCardItemKey:1442`），被 `ui/home` 跨包 import（`HomeScreen.kt:75-78`）——home→game 横向寄生依赖；`GameActionsSheet` 单 composable 440 行（491-930）。
- **建议**：封面搜索组件迁 `ui/cover/`；工具迁 `ui/common/`；GameActionsSheet 按动作域拆分。

#### P1-3 SettingsScreen 巨型文件 + 引擎设置寄生

- **位置**：`ui/settings/SettingsScreen.kt`（1273 行）
- **现状**：内嵌 `EngineSettingsDetailScreen:660`（供 EngineSettingsActivity 使用）与 `krkrPercentOptions/krkrVcursorOptions:1217-1227`，且被 `EngineScreen.kt:57` 跨包 import `artVersionOptions`——engine→settings 横向依赖。
- **建议**：引擎设置 UI 独立成 `ui/settings/engine/` 子包文件。

#### P1-4 Activity 样板代码 7 处复制

- **现状**：每个二级 Activity 重复 ~25-30 行同一段：`isDarkEffective` 判断 → `enableEdgeToEdge`（含弃用 API `window.statusBarColor`）→ `ProvideAppLocale { TyranorNextTheme { Surface } }` → `finish()` 中 `overridePendingTransition`。涉及全部 7 个二级 Activity（如 `EngineSettingsActivity.kt:21-60`）。
- **建议**：抽 `AppScreenScaffold` Composable 宿主（或轻量 BaseActivity）统一主题包裹、边到边与转场。

#### P1-5 UI 绕过 FIFO 直写持久层（与文档声明不符）

- **位置**：`GameScreen.kt:210`（`EngineScanner.saveRoot`）、`GameScreen.kt:334-335`（`removeRecentGame/removeQuickLaunch`）、`SettingsScreen.kt:156-157/413-414/458`
- **现状**：CONTEXT.md 声明 "MainLibraryViewModel 用单线程 FIFO 队列串行化**所有**持久化命令"，实际存在**两道并行 FIFO**（VM Channel 队列 + `GameLibraryRepository.writeScope` 队列），UI 直写路径只进后者；靠仓库层第二道队列兜底才未出错。
- **建议**：明确唯一写入口为仓库层 `post()`，文档改为如实描述；UI 侧写入统一收敛到 VM 命令队列或仓库门面。

#### P1-6 VM 越层引用 DAO 常量

- **位置**：`MainLibraryViewModel.kt:14` 直接 `import ...core.game.storage.GameLibraryDao`（仅用 `MAX_QUICK_LAUNCH` 常量，:189/:253）
- **建议**：常量由 `GameLibraryRepository` 门面转发。

### 2.3 engine 层（P1/P2）

#### P1-7 Intent extras 契约无统一常量类（最脆弱契约）

- **现状**：`path/gamePath/projectRoot/gamedir/rootUri/themeColor*` 等 **20+ extras** 是散落两侧的字符串字面量，仅个别有常量（`Anime4kRuntime.EXTRA_MODE`、`KrkrStartupDialogPolicy.EXTRA_ENABLED`）；协议松散（extras 约定 + 共享 prefs 隐式通道 + Intent 显式类引用三条通道并存）。
- **建议**：engine 模块定义 `LaunchContract` 契约常量类，app/engine 双侧引用；逐步将共享 prefs 通道显式化。

#### P1-8 tyrano / rpgmaker 包复制粘贴（~1500 行）

| 文件对 | 重复度 |
| --- | --- |
| `com/core/tyrano/VirtualMouseLayer.kt` ↔ `com/core/rpgmaker/VirtualMouseLayer.kt` | **逐字节相同**（423 行 ×2） |
| `AsarArchive.kt`（两包） | ~90%（rpgmaker 版多一个 `openStream`） |
| `TyranoStorage` ↔ `RpgMakerStorage` | 大部分相同（diff 仅 65 行） |
| `TyranoLocalHttpServer` ↔ `RpgMakerLocalHttpServer` | 已部分分叉 |

- **建议**：抽 `com.core.webcommon` 共享包；HTTP 服务器差异部分参数化。

#### P1-9 引擎宿主 Activity 上帝类

- **现状**：`TyranoActivity`(1061 行)、`RpgMakerActivity`(1005 行)、`KirikiroidLauncherBaseActivity`(881 行) 混杂窗口管理/设置读取/HTTP/注入/存储；引擎 Activity 逻辑基本无测试（仅 4 个相关单测）。
- **建议**：拆出可测的非 Activity 逻辑（设置解析、注入脚本准备、存储路径决策），Activity 只留生命周期与窗口管理。

#### P2-7 engine 内业务逻辑越界 + 隐式 prefs 耦合

- **现状**：engine 直读写 app 共享 prefs（`TyranoActivity.kt:99` 外部网络开关、`ArtemisLauncherBaseActivity.java:198` 回写成功版本、`OnsSettings` 自有 prefs 迁移）；`NativePluginManager/Installer`（SHA256 校验、启用状态机）偏 app 侧资产管理；`EngineLauncher.safeSharpnessValue` 注释自认与 `OnsSettings.safeSharpness` 一致（同一校验两处维护）。
- **建议**：prefs 键与读写统一收口到 `EnginePrefs` 契约锚点（现状已部分做到）；sharpness 校验等双侧一致逻辑单点化。

### 2.4 横切关注点（P2）

#### P2-1 无 DI + 初始化顺序靠注释

- **现状**：~38 个 object 单例硬编码互引；`EngineScanner.init` 块注册 `GameLibraryRepository.onPersistFailure` 回调；初始化顺序靠 `TyranorNextApplication.onCreate`（18-27 行）注释约定（PrefsRenameMigration 必须先于一切 prefs 读）。
- **建议**：不强制引入 DI 框架；至少建手工 `ServiceLocator` 收口单例图，使依赖显式、可注入替身。

#### P2-2 DB + prefs 双写过渡架构（最大一致性风险源）

- **现状**：`GameOverridesRepository` / `GameLibraryRepository` prefs 镜像 1.5s 防抖写回；跨进程 prefs 缓存不可见，引擎子进程写回的 touchpad 字段会被整条镜像覆盖，靠启动时 `syncFromPrefs` 回灌兜底（`GameOverridesRepository.kt:44-84`，cacheGeneration 重试循环可见复杂度）；注释自认"彻底收口为后续项"。
- **建议**：长期收敛为单一事实源（DB）；引擎子进程回写走显式 Intent/文件协议而非 prefs。

#### P2-3 Room 存储层风险

- **现状**：`GameLibraryDatabase` `fallbackToDestructiveMigration(OnDowngrade)`（44-46 行）+ `exportSchema=false`——无迁移路径的升级会清库，防抖窗口内崩溃丢增量；**单 DAO 承载全部 5 张表**约 20 个查询（`GameLibraryDao.kt` 137 行）；`EngineScanner.kt:13` 直接 import DAO 类型跨包触达存储细节。
- **建议**：启用 `exportSchema` 并补正式 Migration；DAO 按实体拆分；DAO 类型收敛到 storage 包内。

#### P2-4 线程工具无统一收口

- **现状**：无 `runBlockingIo` 类统一工具；`runBlocking + withContext(IO)` 三行模板在三个仓库重复实现（`GameLibraryRepository.kt:370-376` / `GameOverridesRepository.kt:98-103` / `EngineDetectionRepository.kt:101-102`）；46 处手写 `withContext(Dispatchers.IO)`；全局 CoroutineScope 2 个（GameLibraryRepository.writeScope、CoverScrapeTaskManager.scope）；`SettingsScreen.kt:137` 组合期 `remember {}` 直读 `EngineScanner.loadRoots`（依赖预热缓存兜底）。
- **建议**：抽统一阻塞门面工具（含主线程断言）；组合期读取改为预热缓存 + 修订号订阅的单一模式。

#### P2-5 日志无收口

- **现状**：app 52 处 + engine 129 处裸 `android.util.Log`，TAG 字符串字面量散落；无级别控制、release 无剥离策略；engine 以 SharedPreferences 当诊断日志（`NativeBridge.recordOpenDiagnostic`）；无 UncaughtExceptionHandler。
- **建议**：轻量日志门面（统一 TAG 前缀 + release 剥离/降级策略），渐进迁移。

#### P2-6 Navigation3 形同虚设

- **现状**：`NavigationKeys.kt` 仅一个 `Main` NavKey，`Navigation.kt` 只转发 `MainScreen()`；真实导航 = 手写 Tab 状态（`MainScreen.kt:83`）+ 10 个 Activity 跳转；`MainScreen` 四 Tab × 7-8 回调 props 透传持续膨胀。
- **建议**：决策去留——真用 Navigation3 承接二级页，或删依赖；短期至少把 `MainScreen` 回调 props 收敛为单个 `LibraryActions` 数据类。

#### P2-8 弹窗三套并存 + 加载态重复

- **现状**：自研 `AppAlertDialog`（8 处）与原生 `Dialog`（`GameShortcutCropDialog.kt`）、`ModalBottomSheet`（`GameScreen.kt:53`）并存；loading 标志 + CircularProgressIndicator + 空态文案模式在 5+ 处手写，common 无统一异步状态组件。
- **建议**：ModalBottomSheet 场景保留（交互形态不同），原生 Dialog 迁 AppAlertDialog；common 增加 `AsyncStateContent`（loading/empty/error 模板）。

#### P2-9 死代码与死配置

- `ui/common/PlaceholderPage.kt`（38 行）零引用
- `app/build.gradle.kts:210/235-247` 声明 6 项 androidTest 依赖，但 `app/src/androidTest` 源集不存在
- 伪公共组件：`LiquidGlassNavigation.kt`（282 行，common 最大文件）仅 MainScreen 一个调用点
- **建议**：删除 PlaceholderPage 与 androidTest 死配置（或补测试）；LiquidGlassNavigation 移至 `ui/main/`。

#### P2-10 测试可测性弱 + 文档出入

- **现状**：core 全部 Store/Repository 强依赖 Context 的 object，无法直接实例化；如 `RpgVersionSettingsTest` 退化为常量断言；EngineLauncher 30+ 处合并逻辑零测试。文档出入两处：① AGENT.md core 禁 Compose vs 实际 4 文件 import runtime（见 P0-4）；② CONTEXT.md FIFO"所有持久化命令"唯一入口 vs 实际双道 FIFO（见 P1-5）。

## 4. 原则约束（重构期间不得破坏）

1. 依赖方向固定 `ui → core → engine`；engine 零反向依赖、ui 零引擎包直引（现有 0 违规必须保持）。
2. core 对外 API 语义三分：操作失败抛异常（未来 AppException）、无结果返回 null/空集合、调用方容错自行 runCatching。
3. 所有持久化写必须经仓库层单线程队列（唯一串行化保证点）。
4. 每步重构用 `./gradlew assembleDebug --no-daemon` + `checkHardcodedUiStrings` 验证；关键改动用 rg 核验落盘（历史教训：Edit 工具偶发假成功）。
5. 术语变更同步 `CONTEXT.md`，与代码冲突时以代码为事实源当场指出（AGENT.md 文档纪律）。
