# 游戏与引擎互切、设置返回：四对 release 对照

这轮比较移植前相邻的两个 release，A 为上一轮包（SHA-256 前八位 `7cf8b1de`），B 为候选包（`a175c30f`）。可重复的结果是少做了一部分应用侧工作；没有测出切页和设置返回都稳定减少可见卡顿。

## 改了什么

- 游戏卡片仍使用各自的时钟、延迟和取消机制。仅在同一入场作用域、同一弹簧、同一纳秒时刻、正零初速度的标准 0→1 入场段复用求解结果，值和速度分别缓存。其他起点、目标、中断及普通档沿原路径。
- 返回时让黑色遮罩单独绘制，颜色未变不重复使其失效；正文、玻璃采样与窗口转场保持原层次。同一次恢复的引擎安装状态查询供行和弹窗共用，下次恢复仍重新查询。
- 基线诊断中粒子写入 420 次、实际绘制 420 次，未据此更改粒子数或时钟。对分页图层另做的属性特判没有稳定收益，未保留。

## 采集和结果

同一真机逐轮核对安装包 SHA-256，使用 speed AOT，强停后确认冷启，再做相同预热。顺序为 **A1 B1 B2 A2 B3 A3 A4 B4**。共 16 条正式 Perfetto 轨迹、48 次切页、24 次返回。返回窗口从设置 Activity 的 pause 起取 600 ms；主线程与 RenderThread 运行时间按调度切片计，不含等待。正式包无诊断标记；下列复用次数来自另录的插桩 release，不能换算为正式包 CPU 降幅。

| 方向 | 应用侧观察 | 正式包显示晚呈现，A → B |
| --- | --- | --- |
| 游戏→引擎 | 12,680 次标准弹簧值或速度请求中复用 8,284 次（65.3%） | 0/866 → 0/865 |
| 引擎→游戏 | 3,128 次中复用 740 次（23.7%）；CPU 随轮次变化 | 0/866 → 0/865 |
| 设置返回 | 主窗口显示列表录制的主线程 CPU 每次返回平均值，四对分别少 0.56、0.21、0.91、0.26 ms | 1/680 → 0/590 |

晚呈现的分母是成功关联的实际 display token。返回窗口内 RenderThread 总运行时间四对分别少 15.66、13.60、6.04、12.55 ms，但应用提交的帧数也不同。按可比帧预算统计，主线程每帧运行时间反而多 0.016–0.086 ms；应用自身错过截止时间为 **2/679 → 4/585**。总 CPU 下降不等于每帧更快，也不能把少提交的应用帧当成少刷新了屏幕。

## 画面及回归

另录的手机画面中，可见起步到落稳：进引擎 448.7 → 432.0 ms（约差一录制帧）、回游戏 433.6 → 433.4 ms、设置返回 366.8 → 366.7 ms。两包在设置返回的最后 1 像素都重复一帧；静止时 23 条语义记录及抽取的 49,670 个前景像素一致。动态粒子、系统栏与独立录屏相位不适合做整屏逐帧比较。普通档核过原路径、窗口资源与专项测试，未单独录 A/B。

源树该轮手机专项 13 项通过，平板另通过相同位置、相同进度的遮罩像素对照。JVM 2,095 项中 2,069 通过、26 跳过；应用 lint 为 0 错误、335 警告、10 条提示。这些结果属于本轮两包，不是后续[动效入口抽取](motion-v2-abstraction-back.md)或本 PR 移植后的性能结论。
