# 统一引擎宿主启动加载界面实施计划

- 日期：2026-11-13
- 状态：全部纳入宿主代码接入完成；工程与本轮受控设备验收已完成，未覆盖的真实样本 / 设备矩阵见专项验收记录。
- 范围：App 可控的内置引擎宿主；保留以下调研基线与分阶段计划，实施事实另行记录。

## 1. 目标与边界

统一各内置引擎宿主的启动加载视觉、提示、生命周期清理和失败呈现；保留每个运行时自己的启动流程、线程模型、Surface 与输入行为。

目标是从宿主具备可绘制窗口起，到可以露出游戏画面为止提供一致的加载层。必须区分“启动调用返回”“窗口建立”“首帧提交”“游戏交互就绪”，不得把它们统称为同一种成功。

不承诺首帧内容一定是标题画面或可操作画面；黑色也可能是合法游戏首帧。不通过截图颜色推断成功，不伪造百分比进度。

### 纳入范围

- Kirikiroid2 1.3.4 / 1.3.9（Cocos）。
- Siglus、FVP、RealLive / AVG32 / UK2（Framebuffer）。
- Ethornell / BGI。
- ONS、krkrsdl3、System35、System4（多套 SDL 宿主）。
- Artemis 各宿主（官方及 clean 内核）、CMVS（NativeActivity）。
- Tyrano 网页壳（含其承载的 Web 游戏）、独立 RPG Maker MV/MZ Web 宿主。
- SystemNNN。

### 不纳入首轮改造

- 外置 APK 引擎模块、第三方 APK 运行时模块、外置模拟器、安卓游戏的对方窗口。
- 把存档同步、补丁、SAF 准备、运行库解压等 App 启动前工作迁入 engine。
- 新增独立加载 Activity、跨 App 悬浮窗、强制统一所有 Activity 的父类。
- 为加载层更换游戏渲染路径、启用画质滤镜或修改原生预编译运行库。

外置启动可以继续展示 App 交棒前的忙碌状态；无法仅靠主 App 控制对方窗口或确定对方首帧。

## 3. 共用组件设计方向（建议，非既有 API）

在 `engine/src/main/java/com/core/engine/` 下增加原生 View 加载组件及轻量控制器；具体类名实施前与既有结构对齐。不引入 Compose，不依赖 app 的 UI、主题类或页面，不使用全局 Activity 引用。

### 3.1 职责分配

共用组件负责：

- 标题、无确定进度转圈、阶段提示、错误提示的统一布局。
- engine 自有三语言资源与无障碍描述。
- 全屏遮罩及可读内容的系统栏 / 刘海安全区处理。
- UI 线程内挂载、更新、淡出、移除、取消动画和回调清理。
- 加载阶段明确消费遮罩区域触摸，阻止穿透；这是新增接入契约，当前各宿主遮罩未显式消费触摸，不能当成已有保证。返回交由各宿主既有退出处理，不改成统一 finish。

宿主适配负责：

- 挂载到合适内容容器并维护层级；不得隐藏或停止底层 Surface 来等待首帧。
- 接入真实启动状态、必要对话框、就绪和失败信号。
- 按已有线程规则初始化、渲染、停止和释放引擎。
- 决定方向锁、沉浸模式与系统栏恢复时机；共享 View 不全局接管窗口策略。

### 3.2 最小状态与约束

建议语义：加载中 → 可展示 / 失败 / 已销毁。首次展示成功后，常规暂停、切后台、视频返回或 Surface 重建不能自动重新进入首次启动加载。

- 每个宿主实例持有自己的控制器；涉及异步 Surface 变更时校验实例和 generation。
- 主动退出后到达的 native、渲染或 Web 回调必须忽略。
- show / ready / fail / dispose 应幂等；失败不能随后被迟到 ready 覆盖。
- 不把后台暂停视为启动失败；暂停期间是否计入超时必须显式定义。
- 需要用户操作的对话框、授权、字体选择等不能被全屏加载层盖住。
- 错误由宿主现有类型 / 错误出口驱动，共用组件不新增 core→ui 错误协议。
- 超时不直接宣告加载成功；保留 krkr 既有 20s 兜底作为单独兼容行为，首轮不推广也不擅自移除。该兜底即使没有场景通知也会尝试揭层，存在弹窗时每 500ms 延后；必须记录为 fallback reveal，不能记作首帧成功。
- dispose 只清理加载组件，不能替代引擎 teardown：krkr 销毁会清 listener 并终止专用进程；Ethornell 依赖异步 native close ACK；Framebuffer 有自己的停止帧循环与关闭 handle 顺序。

### 3.3 完成证据的等级

每个适配必须记录实际采用的证据，而不是只写 ready：

1. 初始化成功：运行库 / 句柄建立；不能证明已有画面。
2. 窗口可用：Surface 已建立且尺寸有效；不能证明已提交游戏帧。
3. 首帧提交：当前输出代际成功交换缓冲，或有效 Bitmap 已进入实际绘制流程；仍不承诺物理屏幕已经扫描显示。
4. 框架就绪：引擎特定的场景 / 资源就绪通知；须注明其与首帧的先后关系。

首轮替换不能把既有弱证据改名为强证据。没有可靠完成信号的宿主可以先验证加载组件挂载原型，但不得进入全量发布完成名单。krkr 场景 hook + 延迟属于特定兼容判定，不能冒充第 3 级。

### 3.4 视觉与主题

复用 engine 的 `EngineThemeColors`、`EngineUiText` 与既有 `LaunchContract` extras。颜色与语言读取启动 Intent 快照；`ThemeColorPayloadStore` 是 App 进程内状态，宿主独立进程不能直接读取。`EngineUiText` 从宿主 Activity Intent 创建本地化资源 Context，不能丢失 Activity 上下文后假设仍可读取语言 tag。注意现有 palette.background 固定为黑色，Web root / WebView 当前另有硬编码黑底，并非统一由 palette 驱动；不能直接把浅色 palette.text 绘到黑背景上，也不能把 card 直接当页面底色。

实施时先明确加载层底色与前景色的配对规则，再决定是否扩展已有纯数据主题载荷；不能继续从 app R 动态查找资源，不能沿用 `com.apps.LauncherActivity` 反射作为新组件依赖。

首轮优先使用一致、对比度充分的纯色加载背景与主题色转圈，不复制应用层粒子 / 玻璃渲染。保持无障碍字体缩放与横竖屏安全区，标题 / 提示尺寸以专项视觉确认结果为准。

## 4. 分阶段实施任务

依赖顺序：P0 冻结边界 → P1 共用组件及已有加载层视觉迁移；P2、P3、P4 在各自挂载与就绪契约核实后可分别推进；P5 依据真实验收结果收尾。P1 的“视觉已迁移”与“可靠完成信号已补齐”分别记录，不以一个勾选项替代两者。

截至本次静态核对，SDL / Artemis / CMVS 没有已发现且独立于滤镜的通用可靠首帧出口；这是待解决事项，不是已有能力。需要运行库修改的分支单独估算与排期，未验证分支不能随 P1 宣告覆盖完成。

### P0：事实核对与接入契约

1. 对照 manifest、EngineLauncher 与各内核分支形成完整宿主矩阵，标明进程、父类、内容容器、native 初始化发生时机。
2. 每个宿主记录窗口 token 可用时点、最早真实可绘制时点、super.onCreate 同步阻塞路径，以及完成信号、失败出口、退出路径、用户交互等待和 Surface 重建入口。SDL 父类先同步 loadLibraries 再建立内容层，NativeActivity super 也进入 native loader；仅在 super 返回后创建 View 无法覆盖此前耗时。若要求从 native 初始化前即显示，必须先以原型验证新的准备阶段或窗口启动背景策略，不能靠 post 后立即执行重活来宣称可绘制。
3. 对 native / SDL / Web 完成信号进行静态核对；未知项保持未知，不以超时补齐。
4. 核对主题载荷、三语言资源和 API 26 最低兼容要求。
5. 决定首轮视觉契约与超时策略；没有可靠首帧信号的宿主不能标记为已完成首帧统一。

退出条件：矩阵无漏项；每个不确定项有明确调查任务及阻断范围。

### P1：共用组件与已有加载层替换

1. 实现共用加载 View / 控制器及生命周期清理；覆盖触摸拦截、失败后迟到成功、dispose 后回调和首次加载去重。
2. Kirikiroid2 只迁移 UI 构造与失败文案展示，保留 ORIGIN_MODE、native ready、弹窗等待、方向锁及 20s 兼容兜底。
3. Siglus 迁移视觉：滤镜代理路径复用 onFirstFrame 与代理代际校验；直出 onStepped 只能记作既有弱证据，首帧提交需另行核对。
4. FVP、Framebuffer、Ethornell 按已核对信号接入；弱信号不得在文档中称为“真实首帧”。
5. 清理被替代的重复 UI 构造，不顺手重构宿主生命周期。

退出条件：已有加载路径的正常 / 失败 / 返回行为无回归；FVP 当前非零 step 直接 finish，视觉迁移不静默改其失败语义，资源与销毁检查通过。

### P2：SDL 家族

1. 分别检查 SDL2（ONS）、SDL2 app32（System35/4）、SDL3（krkrsdl3），优先放在项目自有宿主适配，避免大改 vendor SDLActivity。
2. 验证挂载不改变 Surface 尺寸、焦点、渲染线程启动条件；加载层不得遮断必要的窗口 / native 生命周期事件。
3. 找到与是否启用画质滤镜无关的首帧通知路径；软件帧缓冲 / GLES / 代理路径分别验证。krkrsdl3 现有 install 在未启用滤镜时直接返回，还受固定运行库身份约束，不能直接推广到这些路径。
4. 原生库缺失、运行库包损坏、native 初始化失败仍走原错误处理。

退出条件：各 SDL 分支均有明确完成语义；仅有窗口创建回调的分支不算验收通过。

### P3：NativeActivity 与 SystemNNN

1. Artemis 各官方版本与 clean 内核分别核对；CMVS 单独核对，不能假设其运行库可直接修改或已有回调。官方图形 hook 依赖有效滤镜请求，clean 不安装该 hook；代理 submitted 还发生在实际 swap 前，直出没有相同通知。CMVS 既有方案记载 Vulkan / wgpu 路径，必须核对固定运行库的实际呈现能力，不用 GLES hook 代替。
2. 用最小原型确认普通 View 覆盖 native Surface 是否成立；检查视频窗口和 Surface Z-order。可对照 `ArtemisPerformanceOverlay` 的应用内 `TYPE_APPLICATION_PANEL` + 宿主 token，作为不替换 NativeActivity content 的备选；它不是跨 App 悬浮窗，不需要该类悬浮权限。现有诊断条的 NOT_FOCUSABLE / NOT_TOUCH_MODAL 旗标不能照搬到需要拦截触摸的全屏遮罩，必须验证与游戏对话框的层级。
3. 如果完成通知需更新预编译库，另列来源、ABI、固定校验、许可证与设备验收任务；未完成前保留为阻断项。
4. SystemNNN 在接入前先决定稳定父容器 / 明确重挂策略：startGame 与 message 会清空 root，stage 又不是全屏 root，必须验证覆盖范围与安全区。授权 / 选择 / 错误页立即可见，仅在前置操作完成进入 startGame 后考虑忙碌层；在首个游戏自有 logo / opening / title 或有效 frame 开始呈现时退出，不等到进入 story 或可交互才结束。

退出条件：正常首帧与等待用户操作两类路径都能正确离开遮罩，不引入新后台 / 销毁竞态。

### P4：Web 宿主

1. 加载层挂在 WebView 外，保留现有 JS 注入、导航白名单、错误处理与输入层逻辑。
2. 区分初次主框架导航、重定向、子资源请求、游戏内部导航、游戏重载和 WebView renderer 退出。
3. 两个宿主目前没有 onPageCommitVisible / onRenderProcessGone 处理；先新增最小原型验证初次主框架可见信号（必要时配合视觉状态回调），明确它不是游戏资源就绪；补足 renderer 退出的失败出口，不能把 onPageFinished 直接定义为游戏就绪。
4. 已知 Tyrano / RPG Maker 框架的资源就绪适配与通用 WebOther 回退分开，不能要求任意网页暴露统一 JS API。
5. 原生加载层退出后保留游戏自身资源加载画面；失败可退出，不能无限遮挡游戏错误。Tyrano“返回标题”会 reload，此路径不自动重开首次启动遮罩；若需要重载提示，单独定义状态。
6. 验证同游戏重复派发、切换游戏 recreate、about:blank 销毁导航与迟到回调；控制器归属当前 Activity 与初始导航代际。主框架可见后继续保留现有 JS 补注入，不以加载层退出为由删掉 onPageFinished 逻辑。

退出条件：离线大资源、重定向、导航失败和网页内部切场景均无永久遮罩。

### P5：文档、清理与全量验收

- 同步 SPEC、README、CHANGELOG；架构职责变化时更新 ARCHITECTURE。
- 只有项目术语发生变化才更新 CONTEXT；本计划不是 ADR，不满足三门槛不创建 ADR。
- 删除实际替换后的重复代码和过时注释；未接入宿主在状态表中保留明确限制。
- 不把组件编译、合成 Surface 测试或静态 hook 检查写成真实游戏兼容性通过。

## 5. 验证矩阵

| 维度 | 必须验证的场景 |
| --- | --- |
| 正常启动 | 每个宿主 / 内核至少一个已知样本；冷启动、同进程再次请求、运行库首次准备与已缓存；分别记录 App 预派发准备、宿主启动、交互等待、首个宿主内容可见时间点，标明加载层实际覆盖区间 |
| 图形路径 | 支持的关闭滤镜、启用滤镜、软件帧缓冲、直出 / 代理回退 |
| 中断 | 加载时返回、切后台再回来、销毁后迟到 ready、native 错误、缺库、无有效游戏内容 |
| 交互 | 加载期间点击游戏区域不触发底层输入；krkr 启动弹窗、字体 / 存储授权、错误确认、视频启动不被遮罩拦截 |

## 8. 实施记录（2026-11-13）

本节记录当前实施事实，前文第 2 节保留实施前调研基线，不应据其推断当前代码仍缺少共用加载层。

### 8.1 已落实的代码

- `EngineStartupOverlay`：原生 View 统一黑底、白色标题、灰色提示、Intent 主色转圈、三语资源、安全区、触摸消费、150ms 淡出与幂等 dispose；失败后迟到 reveal 无效。NativeActivity 可挂应用内子窗口，不抢主窗口焦点。
- `EngineSurfaceReadyProbe` / `EngineSurfaceReadyState`：单次在途 PixelCopy，校验 epoch、Surface 实例与 generation；不读取颜色，合法黑缓冲区同样有效；120 秒有效前台时间截止，暂停 / 失焦停止计时，超时失败不揭层。
- `EngineSurfaceStartupController`：SDL 与 NativeActivity 共用 SurfaceHolder 管理、暂停 / 焦点门控、回调解绑和清理，避免各宿主复制探针实现。
- Kirikiroid2 1.3.4 / 1.3.9：视觉迁移，保留场景通知、弹窗等待、20 秒兼容揭层与方向守卫；黑色加载期固定浅色系统栏图标。
- Siglus：代理保留成功 swap 的首次输出信号，直出改为当前 Surface 可复制缓冲区；FVP / Ethornell 从 step / RUNNING 改为缓冲区信号。
- Framebuffer：首次有效 Bitmap 进入 `onDraw` 后通知揭层，销毁时释放监听。
- ONS / krkrsdl3 / System35 / System4：接入共享控制器，关闭滤镜也走相同探测机制，不改变渲染路径。
- Artemis 官方 / clean 与 CMVS：保持 NativeActivity 现有 taken Surface，转发 SurfaceHolder.Callback2 生命周期，加载 UI 使用应用内子窗口；未改预编译库和 native ABI。
- Tyrano / 独立 RPG Maker Web：初始主框架 commit 或视觉状态 callback 后揭层；空响应有 DOM 可绘制回调补充；被宿主消费的首次导航立即失败且可返回；初始主框架网络 / HTTP 失败不能被迟到成功覆盖；renderer 退出清理失效 WebView。
- SystemNNN：固定 root + 可替换 contentHost；必要授权 / 选择 / 错误界面不被遮挡，游戏 logo / opening / title / frame / modal 可布局后揭层；失败、重试和销毁用 attempt generation 拒绝迟到事件。

### 8.2 验收口径

工程编译、状态机回归、真实 Android Surface 夹具、真实私有 Web / JNI 宿主路径与商业游戏兼容性是不同证据。当前所有纳入宿主已完成代码接入；完整设备矩阵及每个商业样本的兼容性仍需逐项记录，不能由共用组件或少数夹具外推。

详细命令、实际设备结果、截图、运行库身份及未验证项见 [统一加载界面验收记录](统一引擎宿主启动加载界面验收记录.md)。
